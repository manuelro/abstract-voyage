# Assessment: adopting Motion (motion.dev) for the config panel's drag

## Context

`components/Panel`'s config shell (`PanelShell`) just got hand-rolled drag-to-reposition, persisted position, a real damped-spring release settle, and a configurable opacity fade (`usePanelDrag.ts`, `components/Panel/config/usePanelPosition.ts`). The user asked whether Motion (npm package `motion`, import path `motion/react` — the successor to `framer-motion`) would be a better foundation for this than the hand-rolled implementation. This doc is the requested assessment plus a concrete adoption plan, so the decision can be made with both sides on the table rather than assuming either way.

## What Motion would actually replace

Verified against Motion's own current docs (fetched live, not from training-data memory, since API/package-naming has changed over time):

- **`drag` prop** (`<motion.div drag />`, or `drag="x"`/`"y"` to lock an axis) — would replace the entire hand-rolled pointer state machine in `usePanelDrag.ts` (`onPointerDown`/`handlePointerMove`/`endDrag`, the window-level listener add/remove, the `DRAG_START_THRESHOLD_PX` click-vs-drag distinction).
- **`useDragControls()` + `dragListener={false}` + `dragControls.start(event)`** — Motion's documented mechanism for "drag the element from a different handle than the element itself," called from the handle's own `onPointerDown`. This maps directly onto the requirement that dragging is initiated from `.panelHeader`/`.panelLauncher` while the thing that actually moves is `.panelFrame`.
- **`dragConstraints={{ top, left, right, bottom }}`** — would replace `clampOffset`'s manual viewport-bounds math.
- **`dragElastic`** (0–1) — built-in resistance/give past constraints, which the hand-rolled version doesn't have at all today (mine hard-clamps at the edge instead of giving elastically).
- **`dragMomentum`** (default `true`) + `dragTransition={{ bounceStiffness, bounceDamping }}` — real release inertia derived from actual pointer velocity at release. **This is a genuine capability gap in what I just built**: my spring integrator starts release velocity at zero (documented deliberately, since it wasn't in the original ask) — it settles smoothly but never "flicks." Motion's does, for free.
- **`onDragEnd`'s `info.point`/`info.offset`** — would replace the manual `usePanelPosition` write-on-release, though the persistence mechanism itself (localStorage + `useSyncExternalStore`) is unrelated to Motion and stays regardless.
- **`whileDrag={{ opacity: ... }}`** — would replace the hand-rolled opacity `frameStyle` object, with Motion handling the transition timing/easing itself via its own `transition` prop.

Net: yes, technically, Motion is a strong, idiomatic fit for exactly this feature. It was built for this use case, and its drag+spring+constraint system is more battle-tested (multi-touch, pointer capture, RTL) than a from-scratch implementation can be after one pass.

## Why I'd still recommend against it, for this specific panel

1. **This is the only animation-library-shaped gap in an otherwise deliberately library-free motion codebase.** Every other spring/easing/rAF-driven effect in this repo — `useCardLiftPhysics.ts`'s damped-spring elevation, `useStackGestureNavigation.ts`'s `startEdgeSpringForAxis` (the card stack's own edge-bounce, functionally the closest existing feature to this one), `CtaButtonMotionEasing`/`CTA_BUTTON_MOTION_EASINGS`, `AbstractPostDockEasingPreset` — is hand-rolled, and deliberately so: every one of them is parameterized by fields on that feature's own config object (`stiffness`/`damping`/`durationMs`/an easing-preset enum) and rendered through plain CSS custom properties or inline styles, not a wrapper-component's own internal animation engine. `usePanelDrag.ts` was built to match that exact, pre-existing pattern (same `stiffness`/`damping` vocabulary as `verticalEdgeSpringStiffness`/`-Damping`) specifically so it reads as "the same kind of thing" as everything around it, not a one-off using a different toolkit.
2. **Adopting Motion idiomatically means restructuring around `motion.div`.** Motion's value is largely in its declarative `drag`/`whileDrag`/`dragConstraints` props, which assume Motion itself owns the transform/style application on a `motion.div`. `.panelFrame` today is a plain `div` whose style is a plain object assembled from `PanelShellConfig` alongside a dozen unrelated CSS custom properties (surface color, blur, shadow, border...) in the exact same `style={...}` assignment. Adopting Motion "properly" means either wrapping just the frame in `motion.div` (fine, but now two different styling mechanisms — Motion's `animate`/`drag` system and the existing custom-property object — coexist on sibling concerns of the same element) or using Motion only for its imperative pieces (`animate()` driving a value, no `motion.div` at all), which keeps the file's existing shape but captures much less of Motion's actual value (no `drag`/`dragConstraints`/`dragElastic`, since those specifically require a `motion.*` component).
3. **Bundle cost for a dev-only feature.** `components/Panel` is gated by `useAuthoringToolsVisibility.ts` (staging/dev only) — end-user bundle impact is real but smaller than it would be for a page every visitor loads. Still, `motion/react`'s full package is non-trivial even with its "mini" (`LazyMotion` + `domAnimation`, drag-capable) subset; that's a new dependency the project takes on for one component's polish, in a codebase that has otherwise never needed one.
4. **A complete, tested, config-integrated implementation already exists.** `usePanelDrag.ts`/`usePanelPosition.ts` are done, typecheck clean, don't regress the existing test suite, and expose the same operator-configurable fields (`dragSettleStiffness`/`-Damping`/`-MaxDurationMs`, `dragOpacityWhileDragging`/`-TransitionMs`/`-TransitionEasing`) through the same `PanelShellConfig`/`shell.panel.ts` surface as everything else in this panel. Replacing it buys mainly (1) real release-velocity momentum and (2) less code to maintain going forward, at the cost of the dependency and restructuring above.

**Recommendation: keep the hand-rolled implementation.** If the missing "flick" quality (drag fast, release, watch it carry momentum in the direction of the flick rather than always retreating straight toward wherever it was released) turns out to matter in practice, that's addable to the *existing* implementation with a small, targeted change — track velocity over the last few `pointermove` samples in `usePanelDrag.ts` and feed it into `startSettleSpring` as the spring's initial `velocityX`/`velocityY` instead of `0` — no new dependency, same config surface, same architecture.

## If you decide to adopt Motion anyway: implementation plan

1. `npm install motion` (package name is `motion`, not `framer-motion` — that name now redirects to the same underlying library under new branding).
2. In `components/Panel/index.tsx`, replace the plain `<div ref={dragFrameRef} className={styles.panelFrame} ...>` with `<motion.div ref={dragFrameRef} className={styles.panelFrame} ... drag dragListener={false} dragControls={dragControls} dragConstraints={viewportConstraintsRef} dragElastic={0.15} dragMomentum dragTransition={{ bounceStiffness: panelConfig.dragSettleStiffness, bounceDamping: panelConfig.dragSettleDamping }} onDragEnd={handleDragEnd}>` (exact prop values pulled from the same `PanelShellConfig` fields already added).
3. New `useDragControls()` call in `PanelShell`; `.panelHeader`'s and `.panelLauncher`'s own `onPointerDown` calls `dragControls.start(event)` instead of the hand-rolled `onHandlePointerDown` — the click-vs-drag distinction (`DRAG_START_THRESHOLD_PX`) and click-suppression (`onClickCapture`) become unnecessary, since Motion's own `dragListener={false}` + controlled start already handles that distinction internally.
4. `dragConstraints` needs a live viewport-bounds object (or a ref to a full-viewport bounding element) — replaces `clampOffset`; recompute on window resize the same way the current mount-effect reclamp does.
5. `onDragEnd={(event, info) => setPersisted({ x: info.point.x, y: info.point.y })}` replaces the manual persistence write — `usePanelPosition.ts` itself (the localStorage/`useSyncExternalStore` layer) is unchanged and still needed regardless of which drag engine drives it.
6. `whileDrag={{ opacity: panelConfig.dragOpacityWhileDragging }}` with `transition={{ duration: panelConfig.dragOpacityTransitionMs / 1000, ease: <resolve CTA_BUTTON_MOTION_EASINGS cubic-bezier as a Motion-compatible easing array> }}` replaces the hand-rolled `frameStyle` opacity/transition — note Motion's `ease` accepts a cubic-bezier array (`[x1, y1, x2, y2]`), not a CSS string, so `CTA_BUTTON_MOTION_EASINGS`' string values need a small parse step to reuse them here.
7. Delete `usePanelDrag.ts`'s pointer-state-machine and spring-integrator internals; keep `usePanelPosition.ts` as-is.
8. Re-verify: `tsc --noEmit`, `vitest run components/Panel`, and a live check that collapsed-state dragging (the bug just fixed) still works — `useDragControls` on both `.panelHeader` and `.panelLauncher` needs to point at the *same* `motion.div`/`dragControls` instance across the open/closed conditional re-render, same care already taken with `dragFrameRef` today.

This plan is complete enough to execute if you'd rather have Motion's built-in momentum/elasticity than the small velocity-tracking addition proposed above — say the word and I'll implement whichever direction you prefer.
