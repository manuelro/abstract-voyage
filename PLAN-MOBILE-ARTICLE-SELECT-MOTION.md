# PLAN — Normalized article-select motion for MobilePinnedArticleSection's expanded list

## Short list / full list decoupling (2026-09-13)

Operator ask: the short list and full list were architecturally ONE shared DOM element/component (`.panel`, switching between a "short" height/style and an "expanded" height/style) — the short list was, structurally, "part of the collapsible panel." Fixed by splitting into two fully independent elements:

- **`.shortListPanel`** (new) — always mounted, positioned directly below the carousel exactly where the old collapsed `.panel` sat, height fixed at `listHeightPercent`, never resizes, never shows the full list. Contains its own `.shortListRowsViewport` (fixed padding, `overflow: clip`) and its own pre-existing cross-fade settle animation (the `windowStart`-keyed `AnimatePresence` block) — completely unaffected by anything the full-list panel does.
- **`.panel`** (existing element, narrowed scope) — now EXCLUSIVELY the full-list overlay. At rest, `height: 0` and renders no content at all (no more doubling as the short list's resting box). Only grows/renders content while `expanded` or mid-select-sequence (`expandedDisplayRows !== null`). Raised to `z-index: 5` (above the short list's `z-index: 4` and the backdrop's `z-index: 3`) so it visually covers the short list whenever both are mounted (expanded state) — the two never fight for the same box.
- `computeSelectSurvivors` (the helper that used to hand the full-list panel a "final row set" so it could render an interim collapsed-looking state inside itself) is gone entirely — no longer needed, since the short list is a separate element that settles into its own final form via its own existing `windowStart` mechanism, on its own schedule.
- `handleListSelect`'s STAGE-06/07/08 sequence simplified accordingly: once every row has faded out inside the (now full-list-only) panel, that panel just closes (fades to 0 opacity via the existing `panelFadeOpacity` mechanism, then clears its own content) — it no longer needs to reveal a "final survivor" list or mount a sentinel row inside itself, since the short list underneath (already updated the moment `closePanel()` commits `windowStart`) handles all of that independently.
- Deferred CoverFlow commit (from the prior fix) is preserved, now scheduled off the full-list panel's own close completion plus one `listSettleDurationMs` beat, giving the independent short list's own settle animation time to finish before the CoverFlow's translate motion fires — preserving the "list settles, then coverflow catches up" two-beat reveal.
- Focus-restore on close now targets the short list's own viewport (`shortListViewportRef`), not the full list's — the full list's own viewport may already be invisible/closing at that point.

**Verified live**: DOM structure confirms the two are true siblings (short list panel never nested inside the full list panel) at every state; full panel height is exactly `0` at rest; both remain independently mounted while expanded (full list visually on top, covering the short list underneath); after a selection, the full panel's own row count returns to `0` (closed, no content) on its own timeline while the short list settles to its own final 4-row state (survivor rows + "Expand list") independently. Zero console errors, whole-project typecheck clean.

**Caught during verification**: a CSS comment containing the literal sequence `px-*/py-*` accidentally closed the enclosing `/* ... */` comment block early (`*/` is a comment terminator regardless of context), breaking the whole stylesheet's build. Fixed by rewording the comment; worth remembering for any future CSS comment mentioning Tailwind's `*`-suffixed utility naming convention.

## STAGE-07/08/09 collapse-disconnect fix + config-knob audit (2026-09-13)

Operator screenshot evidence: mid-collapse, the row-content padding vanished and the FINAL short list was already fully visible while the panel container was still tall/mid-collapse — directly contradicting the ask that the list must be completely invisible for the entire physical collapse, only appearing once the panel has fully settled.

**Three converging root causes, one symptom:**
1. `proceedAfterFadeOut` revealed the survivor rows to full opacity IMMEDIATELY once the fade-out finished — well before, and then continuously through, the panel's own physical collapse (which only started several steps later). The "final list" was never actually hidden during the collapse at all.
2. The row-viewport's padding className was keyed on the `expanded` boolean, which flips to `false` the INSTANT the collapse *starts* (not once it finishes) — one beat before `expandedDisplayRows` (the content it insets) actually stopped rendering select-sequence content, producing the visible padding snap mid-collapse.
3. **Config-knob audit finding:** `panelCollapseDurationMs` never actually controlled the real CSS collapse duration. `styles.module.css`'s `.panel` rule hardcoded `transition: height 320ms ...` regardless of this config value — the field only ever fed a JS-side wait timer that ASSUMED it matched the real CSS, so changing it in the panel (the operator's own debug config sets it to 1000ms) never visibly changed the collapse speed at all.

**Fix:**
- Restructured the post-fade-out sequence into a strict, EVENT-VERIFIED order (same "listen for the real thing, don't guess" philosophy as the STAGE-06 fade-out fix below): fade-out done (`transitionend`-confirmed) → survivors swapped in **invisibly** (`opacity: 0`, no transition) → `expandedSelectHoldMs` pause → panel collapse begins (`beginCollapse()`) → **wait for the panel's own real `transitionend` on `height`** (new `panelRef`, with a `panelCollapseDurationMs + 200ms` safety-net timer only) → list reveals via a genuine opacity fade-in (`listSettleDurationMs`/`selectMotionEasing`) → sentinel mounts/reveals (unchanged SEL-06a/06b dance, now simply repositioned later in the sequence) → deferred CoverFlow commit (unchanged mechanism).
- Padding condition changed to `expanded || expandedDisplayRows !== null` (new `showExpandedContentStyling`) — but a className fix ALONE would have been silently defeated: the underlying CSS rule (`.panel:not([data-expanded='true']) .rowsViewport { padding: 0 1.5rem; }`) is deliberately UNLAYERED (a prior regression fix's own doc comment explains why), and per the CSS cascade-layers spec, unlayered declarations always beat layered Tailwind utility classes regardless of the className logic driving them. Re-keyed that CSS rule onto a NEW attribute, `data-expanded-content`, set directly on the row-viewport element and driven by the same `showExpandedContentStyling` boolean — independent of the panel's own `data-expanded` attribute, which legitimately needs to flip immediately to drive the real collapse animation.
- Wired `panelCollapseDurationMs` to an actual CSS custom property, `--mobile-pinned-panel-collapse-ms`, consumed by `.panel`'s own `transition: height` declaration — replacing the hardcoded `320ms`. This both fixes the audit finding and makes the new `transitionend`-based wait trustworthy (the JS side and the real animation now provably agree, rather than assuming they do).

**Verified live** (100ms-resolution DOM sampling across the debug config's slowed-down timings): padding stays at a constant 56px through the entire ~1000ms collapse (matching the now-connected `panelCollapseDurationMs`), row opacity stays at exactly `0` for that whole window, the reveal only begins once panel height has fully settled, and the padding only reverts to the collapsed value once the whole sequence completes and the flat render takes back over. Final row order, sentinel, and the deferred CoverFlow commit all still correct; reduced motion unaffected; zero console errors.

## STAGE-06/07/08 final timing fix: transitionend, not a computed duration (2026-09-13)

The rAF+setTimeout heuristic (previous fix, below) still wasn't reliable enough — operator reported the collapse-before-fade-finishes bug persisting. Root cause: even scheduled from inside a `requestAnimationFrame` callback, the wait was still a `setTimeout` computed from `duration + stagger` arithmetic, and `setTimeout` is not guaranteed to fire in lockstep with the browser's own CSS transition clock (timer clamping/drift, background-tab throttling, etc.) — there is no calendar-time guarantee that matches an animation clock exactly, only a good-enough approximation.

**Final fix: stop guessing, listen for the real event.** The LAST row's own `transitionend` event (bubbled up to `rowsViewportRef.current`, filtered to `propertyName === 'opacity'` and `target.parentElement.lastElementChild === target` — every row stays in its original DOM position during STAGE-06, so "last child" reliably identifies the last-starting, last-finishing row regardless of count) is now the authoritative signal that gates STAGE-07 (the array swap) and therefore STAGE-08 (the panel collapse, via `beginCollapse()`). A computed-duration `setTimeout` (`fadeOutTotalMs + 200ms`) remains only as a safety net for the pathological case where the browser never fires the event (e.g. an ancestor hiding the element mid-transition) — it does not participate in the normal-path timing at all.

New refs: `fadeOutListenerCleanupRef` (removes the listener; called on completion, on a superseding new selection, or on unmount) and `fadeOutFallbackTimerRef` (the safety-net timer). `selectSequenceTimerRef` (the old rAF+setTimeout pair) was removed entirely — no longer needed.

Verified live via 25ms-resolution sampling of the last row's real computed `opacity` and the panel's `data-expanded` attribute: opacity reaches `0.0001` (visually indistinguishable from 0), THEN the STAGE-07 swap fires (opacity instantly back to 1, panel still expanded), and only on the NEXT sample does `data-expanded` flip to `false` — the panel never collapses on an incomplete fade, confirmed by direct observation of the browser's own transition state rather than a timing calculation.

## Deferred CoverFlow translate (2026-09-13)

Operator ask: the covered CoverFlow card's own translate motion (position/activeIndex change) must not happen until AFTER the panel has fully collapsed and the short list is back and visible — previously (and in the two paths that still work this way) the commit happened at the same instant the panel *started* collapsing, so the carousel visibly shifted underneath the still-closing/still-partially-visible panel.

**Design:** `onActiveIndexCommit`/the local `position` state are now deferred, for the default (non-scroll-driven, non-reduced-motion) path only, until the SAME post-collapse fallback timer that already existed to reset `expandedDisplayRows` back to `null` (`Math.max(listSettleDurationMs, panelCollapseDurationMs)` after the panel starts collapsing) — by construction, this is after the collapse animation and the short list are both done. Two paths keep the OLD immediate-commit behavior, since deferring wouldn't make sense for either: `scrollDrivenNavigationEnabled` (activeIndex IS the scroll-restoration target, no separate reveal-then-translate beat exists to protect) and `prefersReducedMotion` (no translate animation to protect from being seen underneath the panel in the first place).

**Race handling:** the deferred commit is stored as a closure in `pendingDeferredCommitRef`, run either by its own timer or by `flushPendingDeferredCommit()` — called from every OTHER path that can change the active article (`openPanel`, `commitIndexDirect`) so a newer interaction during the deferred window always wins; the stale closure still runs (for its `setExpandedDisplayRows(null)` side effect) but its position/commit values are immediately overwritten in the same synchronous tick, so nothing stale is ever actually painted.

Verified live: (1) normal selection — the announcement region (activeIndex-driven) stays on the OLD article for ~350ms after the panel visibly finishes collapsing, then updates; (2) rapid re-tap of a different row mid-fade-out resolves correctly to the second pick with no stale artifacts; (3) tapping a plain short-list row during a still-pending deferred-commit window immediately and correctly overrides it — the final state reflects the newer tap, not the stale one.

## STAGE-07/08 timing bugfix, superseded above (2026-09-13)

Regression, reintroduced during the STAGE-04..08 condensation: the fade-out wait (`fadeOutTotalMs`) was scheduled via `setTimeout` in the SAME synchronous tick as the style change that triggers the CSS transition, not from when the browser actually paints/starts that transition (one frame later). This let the panel start physically collapsing up to a frame before the last staggered row had genuinely finished fading out — same class of race already found and fixed once for this component's entrance/exit sequencing. Fix (superseded by the transitionend-based fix above, which replaced this entirely once it proved insufficient on its own): the `setTimeout` is now scheduled from inside a `requestAnimationFrame` callback, same pattern used elsewhere in this file.

## Stage reference (2026-09-13, updated) — durable IDs for future requests

Canonical breakdown of the component's entire interaction lifecycle, not just the select sequence. Use these `STAGE-*` IDs to refer back to a specific point in the flow. STAGE-04 through STAGE-08 were condensed (2026-09-13) into a simpler opacity-only stagger design — see below the table.

| Stage ID | Ref | End-user action | System response |
|---|---|---|---|
| STAGE-01 | — | *(none — rest state)* | Section pinned in viewport; carousel shows the active article's card; collapsed short list (up to N rows, windowed around the active article) + trailing "Expand list" row below it. |
| STAGE-02 | — | Swipes/drags the pinned carousel card | Carousel position tracks the drag live; on release, velocity projects to the nearest article and commits it. Short list only re-windows if the new active row falls outside what's visible. |
| STAGE-03 | — | Taps a row in the short (collapsed) list, not "Expand list" | Active article commits directly (or smooth-scrolls, scroll-driven mode); carousel animates to that card; short list re-windows if needed. |
| STAGE-04 | — | Taps "Expand list" | Page scroll locks; panel grows to expanded height (CSS transition); tap-to-close backdrop appears; full unwindowed row list mounts, each row invisible (opacity 0). |
| STAGE-05 | — | *(automatic, immediately following STAGE-04)* | Every row fades its opacity in, staggered item 1 through item N (`expandedEnterDurationMs`/`expandedEnterStaggerMs`/`expandedEnterEasing`) — opacity only, no scale/transform. List then auto-scrolls to center + focuses the active row; end user may scroll/hover/keyboard-nav once settled. |
| STAGE-06 | — | Taps a row in the expanded list to select a different article | System computes the final row set (tapped row + followers fitting the short-list window) once, up front. Every row stays in the expanded list at its own original position and fades its opacity OUT (opacity only, `expandedSelectFadeOutDurationMs`/`expandedSelectStaggerMs`/`expandedSelectEasing`), staggered in the SAME direction as the entrance — item 1 starts first, the LAST row fades last. |
| STAGE-07 | — | *(automatic, timed)* | Once the last row's fade-out finishes (the whole list is now invisible), the underlying row array is swapped to the final selection order AND opacity is restored to 1 in that same, transition-less update — imperceptible, since nothing was visible a moment before. |
| STAGE-08 | — | *(automatic, immediately following STAGE-07, optionally after `expandedSelectHoldMs`)* | The panel collapses (CSS height transition) around content that is already final and already fully visible — "already ready" per the operator's own framing, not a hidden/mid-reorder list. |
| STAGE-09 | SEL-06a/06b | *(automatic, timed)* | "Expand list" mounts invisible for one frame, then transitions to full scale/opacity at the bottom of the list. Unchanged by the STAGE-04..08 condensation — out of that request's scope. |
| STAGE-10 | SEL-07 | *(automatic, same moment as STAGE-09)* | New active article commits to the parent; backdrop removed; covered carousel card revealed already showing the new selection; scroll unlocks/restores. |
| STAGE-11 | — | *(automatic, timed)* | Once STAGE-09/10 finish, component swaps back to its cheapest steady-state render (same visuals) — back to STAGE-01. |
| STAGE-12 | — | Presses Escape or taps the backdrop while expanded, no selection | Panel collapses immediately via the plain CSS transition — no row-fade/sentinel choreography. Scroll unlocks/restores. Focus returns to the row list. |

`prefers-reduced-motion: reduce` collapses STAGE-04..STAGE-11 into one instantaneous jump straight to the relevant end state (open: full list at opacity 1 immediately; select: STAGE-01 end state immediately).

### STAGE-04..STAGE-08 condensation (2026-09-13)

Previously (v4) these stages ran a `layout`/FLIP-free but still per-row `itemStyle` scale+opacity treatment, animating only non-survivor rows on exit while survivors sat untouched, with a separate array-removal step. Operator simplification: **opacity only, no scale/transform, for both entrance and exit**, and the exit no longer distinguishes survivors from non-survivors — the *entire* visible list fades out together, and only once fully invisible does the row array swap to its final order. This removes the whole "compute survivors, style only the leavers, remove them after their own animation" branching — entrance and exit are now symmetric, single `rows.map(...)` calls. New config fields: `expandedEnterDurationMs`, `expandedEnterStaggerMs`, `expandedSelectStaggerMs` (re-added).

### STAGE-06 direction correction + independent easings (2026-09-13)

Corrected: the exit stagger was initially built in the *opposite* direction from the entrance (last row first). Operator correction — the leaving stagger runs in the **same** direction as the entrance: item 1 fades first, the last row fades last, and the panel only starts collapsing once the last row's own fade-out has finished. Also split the single shared `selectMotionEasing` into three: `expandedEnterEasing` (STAGE-04/05 entrance) and `expandedSelectEasing` (STAGE-06 exit) are now independently configurable, alongside their already-independent durations; `selectMotionEasing` remains for the phases outside this pair (sentinel mount-in, panel collapse sync, post-collapse settle). All three are 4-number cubic-bezier tuples — not exposed in the visual config panel (no field `kind` supports a tuple control) but editable directly on `MobilePinnedArticleSectionConfig`, same precedent as `selectMotionEasing` always had.

## v4 — Single shared AboutTimeline instance + plain inline-style CSS transitions (2026-09-13)

v3's grid-template-rows collapse still produced new bugs (operator screenshots, tapping "Four kinds of dependency"): the list visibly shrank horizontally on select (BUG-8); leaving rows clipped their own text instead of a clean scale-to-zero (BUG-9); once gone, the vertical spacing between the remaining rows didn't match the final list's spacing (BUG-10); the expanded list's own padding was lost right before collapse (BUG-11); item spacing wasn't consistent at all times, suggesting manual positioning (BUG-12); and near the end, a "leaving" list and an "incoming" list briefly coexisted, the leaving one not yet fully invisible (BUG-13).

**Root cause, all six bugs:** v2/v3 rendered the expanded/mid-sequence list as **N separate `renderList([row])` calls** — one isolated `AboutTimeline` instance (its own `<ol role="tablist">`) per row — so each animated row could be individually wrapped in Motion. This silently broke two things `AboutTimeline`/`AboutTimeline.module.css` depend on:
- **Sibling-relative spacing**: `.item:not(:last-child) .row { padding-bottom: var(--about-timeline-row-gap-px) }` only fires when a row has a *later sibling in the same `<ol>`*. A single-row array is always its own last (and only) child, so this rule never matched — the vertical gap between rows was structurally never applied (BUG-10/BUG-12).
- **Width cascade**: `.timeline > :global(div) { width: 100%; max-width: none !important }` targets *direct children* of `.timeline`. Once each row's actual `AboutTimeline` root div sat two wrapper levels deeper (grid wrapper → overflow wrapper → AboutTimeline root), that rule no longer reached it, so it could fall back to a narrower default width (BUG-8). The grid-rows collapse's own `overflow: hidden` (needed for the CSS height-to-0 trick) is also the direct, literal cause of BUG-9's clipping — a technique the operator explicitly ruled out in favor of pure transform/opacity.

**Fix — go back to ONE `AboutTimeline` instance for the whole list, always.** `AboutTimelineRowData` gained one small, optional, backward-compatible field: `itemStyle?: CSSProperties`, forwarded by `AboutTimeline.tsx` onto each row's own `<li>` (`AboutTimelineRow.tsx`) — every existing caller (the desktop About page) leaves it `undefined` and renders exactly as before. `MobilePinnedArticleSection.tsx` now renders `expandedDisplayRows` through a single `renderList(...)` call (real sibling relationships restored, real width cascade restored) and drives each row's enter/leave purely via `itemStyle`: a plain inline `transform: scale(0)`/`opacity: 0` with `transformOrigin: 'top left'` and a `transition` string — no Motion, no `layout`, no grid-rows, no clipping. Sequence:
- **SEL-02**: non-survivor rows get the leaving `itemStyle` (with `transition` declared) applied to an *already-mounted* row — the browser animates the existing element's computed style change on its own; nothing reflows yet since `transform` never changes box size.
- **SEL-03**: once that transition's duration has elapsed, non-survivors are dropped from the array outright — a plain, **unanimated** reflow the browser performs on its own, exactly as requested ("no need to compute this, let HTML and CSS do the work"). This also directly fixes BUG-13: leaving rows are fully gone from the DOM well before the sentinel is even mounted, so there is never a moment with both an "incoming" and "leaving" list on screen.
- **SEL-06a/06b**: the sentinel mounts hidden (no `transition` yet — a fresh mount has no prior frame to interpolate from) then, one committed frame later, flips to visible with `transition` declared, animating the same scale/opacity mount-in.

Verified live (headless Chromium): list width identical before/after select (was shrinking, now isn't); no clipping at any captured frame (including a 20ms-granularity capture using `el.click()` to skip Playwright's own action-wait latency); spacing/padding matches the idle collapsed list exactly, because it now literally *is* the same single `AboutTimeline` instance/CSS.

## v3 — Replace layout/FLIP with CSS grid-template-rows collapse (2026-09-13)

v2 shipped but still produced visible overlap/collision bugs (operator screenshots): non-survivor rows fading out via `layout="position"` + `AnimatePresence mode="popLayout"` repositioned survivors via JS-computed transform math instead of genuine document-flow reflow, causing text to visually overlap mid-collapse; the "Expand list" sentinel could also appear mid-collapse, overlapping still-settling rows.

**Root design correction:** there is no "move the selected row to the top" step to animate at all. `computeSelectSurvivors` already returns `rows.slice(selectedIndex, ...)` — the tapped row is already first in that slice. The only real work is removing the rows that don't survive. Fix: drop `layout`/`popLayout` entirely. Each row is a two-layer **CSS grid-rows collapse** (`display:grid; gridTemplateRows: 1fr ↔ 0fr` on an outer wrapper, `scale`/`opacity` on an inner content wrapper) — a well-known CSS-only accordion technique. Rows stay in **normal document flow** the whole time; removing a non-survivor row shrinks its own real box height to 0, and the browser's own layout/reflow (not JS) carries every other row into its new position for free. Survivors get **zero** animation — they just sit still. The sentinel row uses the identical mechanism in reverse (mount-in from `0fr`/`scale 0.92`/`opacity 0`), gated to start only after every non-survivor's collapse has actually finished.

Config fields `expandedSelectReorderDurationMs` and `expandedSelectStaggerMs` were removed (no reorder step exists to tune). `expandedSelectFadeOutDurationMs` now governs the grid-rows collapse + inner scale/opacity fade together (one duration, both concurrent). Verified live (headless Chromium, same tap scenario as the operator's screenshots — tapping a mid-list row): single coherent list at every captured frame, no overlap, "Expand list" only appears once the collapse has fully settled.

## v2 — Bug analysis of the v1 implementation and corrected sequence (2026-09-13)

**v1 (everything below "## Context") shipped but is wrong.** Operator review against a live build (screenshots, described below) found the motion breaks into two visibly colliding lists with a stale re-flash and an empty-space gap. This section supersedes v1's sequence design; v1's config surface (the six duration/easing fields) stays — only the render/sequencing architecture changes. Root line refs below are to the v1 code as implemented (`MobilePinnedArticleSection.tsx`), not the original pre-v1 baseline.

### What the screenshots show, phase by phase

1. Collapsed short list, article 1 active (baseline). Correct.
2. Panel expanded, full list visible. Correct.
3. **Tap "Four kinds of dependency" (row 4).** Every row fades toward transparent roughly in place — nothing moves to the top, nothing reorders. **Wrong**: the ask was that the tapped row *and* the rows that will survive into the final short list travel/reorder into their final order (staggered), while only the rows that will be dropped fade out. Only rows that *don't* survive should disappear; the survivors should visibly relocate, not just dim.
4. A moment later: two lists are visibly superimposed — one still mid-fade-out (the v1 per-row expanded overlay), another already showing collapsed-list content, overlapping in the same screen region.
5. The **pre-selection, stale-order** short list flashes back on screen (article 1 still marked active/first) — exactly the "outdated list" flash the whole feature exists to prevent.
6. Two lists collide again, one of them a leftover "Expand list" row positioned mid-animation next to content from the other list.
7. A large empty gap opens between the (now correctly shrunk, 4-row) card/list content and the still-oversized panel boundary beneath it.
8. Final frame: correct. Right rows, right order, right sentinel row position.

Frame 8 being correct proves the *target data* (the reordered rows + sentinel) was always computed right — v1's bug is entirely in **how the screen gets from frame 3 to frame 8**, not in what frame 8 contains.

### Root causes (mapped to `MobilePinnedArticleSection.tsx` as implemented)

**RC-1 — Two disconnected render branches for what should be one continuous list.** v1 has three separate JSX branches for the row list: (a) the plain `renderList({ rows, ... })` call for ordinary expanded state, (b) the new per-row `AnimatePresence`/`expandedReorderRows` overlay while `selectingIndex !== null`, and (c) the pre-existing collapsed-list `AnimatePresence` keyed by `windowStart`. The select sequence transitions **(b) → (c)** by flipping two independent state variables (`selectingIndex → null`, `expanded → false`) in the same tick (inside `proceedToCollapse`/`closePanel`). React unmounts branch (b) and mounts branch (c) in one commit — there is no shared identity between the two: Motion's `AnimatePresence`/`layout` machinery in (b) never hands off to (c), so any in-flight animation in (b) is simply discarded mid-flight, and (c) mounts cold. This is the direct cause of frames 4 and 6 ("two lists colliding") — for one paint, remnants of (b)'s DOM (still visually present because the browser hasn't painted the unmount yet) overlap with (c)'s freshly-mounted DOM.

**RC-2 — `windowStart` (branch (c)'s data source) is deliberately stale for ~320ms.** `settlingAfterSelectionRef` (pre-existing, kept from before v1) intentionally holds `windowStart` at its **pre-selection** value until `settleTimerRef` fires, `config.panelCollapseDurationMs` after `closePanel()` starts. But `closePanel()` now runs **immediately after** branch (b)'s reorder already finished — so branch (c) mounts showing the *old* order for another 320ms on top of the reorder the user just watched happen. This is frame 5, the stale-list flash: v1 built a second, independent "settle" animation (branch (c)) that redundantly replays the same reorder branch (b) had just finished, using stale data while it waits.

**RC-3 — Panel height is a discrete CSS toggle, decoupled from actual row-content height.** `styles.module.css`'s `.panel` height is `--mobile-pinned-list-percent` normally, `--mobile-pinned-expanded-percent` when `data-expanded='true'` (`:37-67`) — two fixed percentages, transitioning over a plain 320ms CSS `height` transition. It has no relationship to how many rows are actually rendered inside it at any instant. Because branch (c) mounts a short (3-4 row) list **immediately** when `expanded` flips `false`, but the CSS height transition takes 320ms to visually shrink the panel, there's a window where a short list sits inside a still-tall panel — the empty gap in frame 7.

**RC-4 — Only the selected row animates; survivors don't.** In branch (b), `layout={isSelected ? 'position' : false}` (v1's per-row `motion.div`) — every row *except* the one just tapped has `layout={false}`. The rows that will survive into the final short list (the tapped row's followers) never get a `layout` animation at all, so they never visibly relocate — they only fade in place. This is frame 3's bug on its own, independent of RC-1/2/3.

**Underlying design mistake:** v1 treated "expanded reorder" and "collapsed settle" as two separate animated components with two separate data sources (`expandedReorderRows(rows, selectingIndex)` vs `shortListRows`/`windowStart`) stitched together with `setTimeout` handoffs. That's why frame 8's *data* was right but the *path* to it wasn't — nothing actually carried the in-progress animation state across the handoff. The fix is architectural, not a timing tweak: **one continuous list, one continuous panel, driven by one state machine**, from tap through to the restored "Expand list" affordance.

### Corrected sequence — step IDs

Every step below operates on a **single row list** (`displayRows`, one continuous `AnimatePresence`/`layout` group, one DOM subtree, never remounted mid-sequence) and a **single panel container whose height is driven by that list's actual content height**, not a separate CSS two-state toggle. Step IDs are stable — refer to them by ID (`SEL-*`) in future feedback.

- **SEL-00 (rest, expanded).** `displayRows` = the full row list, panel at `expandedPanelHeightPercent`. (Unchanged from today.)
- **SEL-01 (tap).** User taps row R. Immediately compute `finalRows` = the exact target collapsed-list array for this selection — R first, followed by however many original-order rows fill out the window, plus the "Expand list" sentinel appended last. This is computed **once**, up front, and is the single source of truth for every subsequent step (no second, independently-computed "settle" pass later).
- **SEL-02 (drop, concurrent with SEL-03).** Every row in `displayRows` **not** present in `finalRows` (i.e. not R and not one of R's surviving followers) animates `opacity → 0` and is removed from the list (`AnimatePresence` `exit`, `popLayout` mode so removal reflows siblings via `layout` rather than leaving a hole). Duration/easing: `expandedSelectFadeOutDurationMs` / `selectMotionEasing`.
- **SEL-03 (reorder, concurrent with SEL-02).** The surviving rows (R + its followers) each animate (`layout`, Motion's shared-layout reflow) from their current position to their `finalRows` position. **Staggered**: each row's transition gets a small `delay` proportional to how far it must travel (or simply its index in `finalRows`), so the reorder reads as a cascade, not a simultaneous snap — this is the literal "staggered manner, one after the other" ask. Duration/easing: `expandedSelectReorderDurationMs` / `selectMotionEasing`, stagger step: new config field (see below).
- **SEL-04 (panel follows content, concurrent with SEL-02/03).** The panel container itself carries a `layout` prop (or animates a measured height), so as `displayRows` shrinks from "full list" to "4-ish surviving rows," the panel's own height animates continuously to match — never a discrete jump, never decoupled from what's actually on screen. This single mechanism replaces both the CSS `.panel[data-expanded]` two-state height *for this transition* and RC-3's gap.
- **SEL-05 (hold).** Optional pause once SEL-02/03/04 all report complete (`expandedSelectHoldMs`, default 0).
- **SEL-06 (sentinel-in).** The "Expand list" row — not part of `finalRows`'s animated reorder (it doesn't exist yet in the expanded view) — fades/slides in at the bottom of the now-settled list. This is the **only** new element introduced in the whole sequence; everything else was already on screen and just moved/faded.
- **SEL-07 (commit + reveal).** `expanded` flips `false`, `onActiveIndexCommit` fires, the CoverFlow behind the panel is revealed — exactly today's existing handoff (`closePanel`'s commit/scroll-restore logic), **but now happening after** SEL-00→06 have already produced the correct final on-screen state, not before it, so there is nothing left to "settle into" afterward. `windowStart` is set to match `finalRows` directly (no more `settlingAfterSelectionRef` stale-hold window — nothing is stale by the time this runs, since `displayRows` already *is* `finalRows` from SEL-06 onward).

Reduced motion: SEL-01 computes `finalRows`, then jumps straight to SEL-07 with all durations at 0 — no intermediate frames, matching today's `prefersReducedMotion` contract.

### Implementation plan

1. **Single state, not three branches.** Replace `expanded` (bool) + `selectingIndex` (bool-ish) + `windowStart` (bool for collapsed display) driving three separate JSX branches with one `displayRows: AboutTimelineRowData[]` state (or the sentinel-augmented shape) that is *always* what gets rendered, in *all* panel states (short, expanding, reordering, settling). `expanded` remains as the "is the panel currently in its full-height mode" flag driving body-lock/backdrop/etc., but no longer switches which list component renders — only `displayRows`'s contents do that.
2. **One `AnimatePresence mode="popLayout"` list, always mounted.** Rows keyed by `slideIndex` (already how `AboutTimeline` keys them) so Motion's `layout` animations track identity correctly across `displayRows` mutations — added rows (SEL-06's sentinel) mount fresh, removed rows (SEL-02) exit, survivors (SEL-03) reflow via `layout`, all inside the same persistent `AnimatePresence`/`LayoutGroup` instance. Per-row rendering still goes through `renderList({ rows: [row], ... })` (single-row calls) so it keeps using the shared `AboutTimeline` row markup without editing that shared component.
3. **Stagger.** Add `expandedSelectStaggerMs` to the config (new field, same six-field family as v1's additions) — per-row `layout` transition `delay: index * (config.expandedSelectStaggerMs / 1000)`, computed against each row's position in `finalRows`. Needs a panel field too (`.panel.ts`), same pattern as the five v1 duration fields.
4. **Panel height tracks content.** Wrap the rows container in a `motion.div` with `layout` enabled (or animate a measured `scrollHeight`) instead of relying solely on `styles.module.css`'s `.panel[data-expanded]` discrete height rule for *this* transition. The CSS two-state rule can stay as-is for the *open* transition (SEL entry, tap "Expand list" from the short list) where a discrete jump is correct and expected — it's only the *select* sequence (SEL-01→07) that needs continuous, content-driven height.
5. **Sequencing via Motion's own completion callbacks, not chained `setTimeout`s.** Replace the `selectSequenceTimerRef` `setTimeout` chain with `AnimatePresence`'s `onExitComplete` (for SEL-02) and `layout` transition's `onLayoutAnimationComplete` (for SEL-03/04) to detect when to run SEL-06/07 — removes the brittleness of hand-computed `fadeOut+reorder+hold` millisecond sums silently drifting out of sync with the actual animations (which is part of how RC-1's race happened).
6. **`closePanel`/`windowStart` simplification.** Since `displayRows` already equals `finalRows` by SEL-06, `closePanel`'s own settle step (`settlingAfterSelectionRef`, the second `setTimeout`, the redundant `setWindowStart(Math.max(selectedIndex,0))`) becomes unnecessary for the select-from-expanded path — it can be deleted for that path and kept only for the other close paths (Escape/backdrop/control button) that don't go through SEL-01→06 at all and still want the plain, un-staggered CSS collapse they have today.
7. **Verification** (unchanged intent from v1, re-run against the new architecture): mid-list tap, rapid re-tap mid-sequence (now: does the `AnimatePresence`/`layout` group cleanly interrupt and retarget, not "does a stray `setTimeout` fire late"), reduced motion, first/last-row edge cases, and specifically re-screenshot the frames that were wrong (mid-sequence, immediately post-collapse) to confirm no two-list overlap and no gap.

### Library recommendation

**Stay on Motion (`motion/react`, already the only animation dependency in this file) — don't add a new library.** It already has every primitive SEL-01→07 needs:
- `AnimatePresence mode="popLayout"` + `layout` for the single continuous reorder/remove/insert list (what v1 was missing — v1 used `layout` on exactly one row instead of the whole group).
- Per-row `transition.delay` for the stagger (SEL-03) — no separate stagger library needed for a single flat list this size.
- `onExitComplete` / `onLayoutAnimationComplete` for sequencing instead of hand-summed `setTimeout` durations (fixes the RC-1 race directly).
- `LayoutGroup` if the panel-height-tracks-content wrapper (SEL-04) and the row list end up as siblings that both need to participate in the same layout animation pass.

The actual bug wasn't a library limitation — v1 under-used Motion's own reorder/layout primitives and hand-rolled a two-branch, `setTimeout`-sequenced substitute instead. If a future need arises for much more complex, many-track choreography (e.g. coordinating a dozen independently-timed properties across unrelated DOM subtrees), GSAP's timeline API is the standard alternative to reach for — but introducing a second animation dependency isn't justified here; this sequence is a single list, a handful of properties, entirely inside what `motion/react` already does natively.

## Context

`experiences/abstract/components/MobilePinnedArticleSection/` (mobile `/abstract`) has two list states: **collapsed** (a short, windowed list, active row on top, an appended "Expand list" row) and **expanded** (the full list, body-locked, every row visible). Today, tapping a row while expanded (`handleListSelect` in `MobilePinnedArticleSection.tsx:560-589`) does exactly one thing: it sets `expandedSelectionRef.current` and calls `closePanel()` immediately. `closePanel()` then does the actual motion work, but *only after* the panel has already visually collapsed — there is no in-panel reaction to the tap at all. The full list just vanishes as the panel shrinks.

The ask is to insert a visible, legible step **before** the collapse: react to the tap inside the still-expanded panel — fade out the unselected rows, animate the selected row to the top, reveal the remaining rows below it in exactly the order the collapsed short list will show them — *then* collapse the panel, and only once collapsed, restore the "Expand list" row at the bottom. All motion timing/easing must be config-driven, not hardcoded.

## Normalized sequence description

Five phases, named for reference in code/comments. All are config-driven durations/easing; the panel-collapse phase's duration already lives in CSS (`styles.module.css`) and stays there, but the **new** config surface exposes a matching JS-side duration so phase 4's `setTimeout` can stay in sync with it (same pattern `PANEL_COLLAPSE_TRANSITION_MS` already uses).

1. **Tap** — user selects a row inside the still-expanded panel. Row is not yet visually distinguished from the rest.
2. **Reorder-in-place** (NEW) — panel stays expanded, full-height. Two things animate concurrently inside it:
   - Every row *except* the selected one fades out (`opacity: 1 → 0`), over `expandedSelectFadeOutDurationMs` / `expandedSelectEasing`.
   - The full row list re-sorts to lead with the selected row, followed by the rest in the exact order `shortListRows`-at-`Math.max(selectedIndex, 0)` would show them (selected row first, then subsequent original-order rows) — the now-fading-out rows are still present underneath/behind this reorder (or removed once their fade completes; see "Decision needed #2"). Rows that survive into the final short-list shape (selected + however many follow it) animate to their new position/opacity=1 via `expandedSelectReorderDurationMs` / `expandedSelectEasing`.
   - This phase's *output state* — while still expanded, full panel height — must be pixel-identical in row content/order (not necessarily height, since the expanded panel is taller than the collapsed one) to what the collapsed short list will show a moment later. This is the "must look identical" requirement.
3. **Hold** (optional, likely `0ms` default) — brief pause once phase 2 settles, so the eye registers the new order before the panel starts shrinking. Config: `expandedSelectHoldMs`.
4. **Collapse** — existing `closePanel()` panel-height transition (CSS, `styles.module.css:63`, already reusing the shared `[0.22,1,0.36,1]` easing) — unchanged mechanism, just now starting from an already-reordered list instead of the untouched full list.
5. **Restore expand affordance** — once phase 4's transition finishes (existing `PANEL_COLLAPSE_TRANSITION_MS`-gated timer, promoted to config as `panelCollapseDurationMs`), the short list (already in the correct order, since phase 2 pre-computed it) fades/settles in via the existing `LIST_SETTLE_*` motion (promoted to config), and — because `expanded` is now `false` — `shortListRows` automatically includes the appended "Expand list" sentinel row. No new code needed for this specific step beyond confirming ordering already matches.

`prefersReducedMotion` collapses every phase's duration to `0` (matching the existing pattern at `:458` and `:714/:716/:719-721` — extend it to the new phase 2 fields too, not just phase 5's).

## Config additions (`.config.ts`)

New fields on `MobilePinnedArticleSectionConfig`, reusing the "single shared easing" default (`[0.22, 1, 0.36, 1]`) rather than inventing per-phase curves, per [[feedback_reuse_existing_knobs]]:

```ts
/** Cubic-bezier easing shared by every phase of the article-select motion
 * sequence (in-panel reorder, panel collapse, post-collapse list settle).
 * Defaults to the curve styles.module.css's own .panel transition already
 * uses, so all phases read as one motion language. */
selectMotionEasing: [number, number, number, number];
/** Phase 2 — ms for unselected expanded-list rows to fade to opacity 0. */
expandedSelectFadeOutDurationMs: number;
/** Phase 2 — ms for the selected row + its followers to animate into their
 * final (post-collapse short-list) order/position, still while expanded. */
expandedSelectReorderDurationMs: number;
/** Phase 3 — ms held after the reorder settles, before the panel starts
 * collapsing. 0 = no pause. */
expandedSelectHoldMs: number;
/** Phase 4 — ms for the panel-height collapse. Must match
 * styles.module.css's `.panel` transition duration (currently 320ms,
 * hardcoded there as CSS) — kept here only so the JS-side settle timer
 * stays in sync with it, same pattern the pre-existing (now-promoted)
 * PANEL_COLLAPSE_TRANSITION_MS used. */
panelCollapseDurationMs: number;
/** Phase 5 — ms for the collapsed short list's post-settle fade/slide-in. */
listSettleDurationMs: number;
```

Defaults: `selectMotionEasing: [0.22, 1, 0.36, 1]`, `expandedSelectFadeOutDurationMs: 220`, `expandedSelectReorderDurationMs: 420`, `expandedSelectHoldMs: 0`, `panelCollapseDurationMs: 320` (matches existing CSS), `listSettleDurationMs: 420` (matches existing `LIST_SETTLE_DURATION_S`). Normalizer clamps each duration to a sane range (e.g. `[0, 1000]`) and validates the easing tuple has 4 finite numbers.

## Implementation plan

1. **`.config.ts`**: add the six fields above to the type, defaults, and `normalizeMobilePinnedArticleSectionConfig`. Delete nothing yet — old module constants in `.tsx` get removed in step 3 once their config equivalents are wired through, not before (keeps the diff bisectable).
2. **New `expandedReorderRows` derivation** in `MobilePinnedArticleSection.tsx`: a small pure helper (co-located near `computeWindowStart`, same file) that, given `rows`, `itemCount`, and a `selectedIndex`, returns the ordered array `[rows[selectedIndex], ...rows excluding selectedIndex in original order]` — this is the target order for phase 2's reorder (matches `Math.max(selectedIndex, 0)`-anchored `shortListRows`, per the "must look identical" fact above, but unwindowed since the full list is still visible during phase 2).
3. **New local state** to drive phase 2 independently of `expandedSelectionRef`: e.g. `const [selectingIndex, setSelectingIndex] = useState<number | null>(null)`. When set (non-null), the expanded-list render branch (`:697-702`) switches from the plain `renderList({ rows, ... })` call to rendering `expandedReorderRows(rows, itemCount, selectingIndex)`, with each row wrapped in a `motion.div`/`AnimatePresence` keyed by `slideIndex`: rows other than `selectingIndex` animate `opacity → 0` (fade-out only, no reposition — avoids fighting the reorder animation of the row that's leaving); the selected + trailing rows animate `layout` (Motion's shared-layout reorder, matching Motion's own idiomatic pattern for reordering) with `transition` sourced from `config.expandedSelectReorderDurationMs`/`config.selectMotionEasing`.
4. **Wire `handleListSelect`'s expanded branch** (`:568-583`): instead of calling `closePanel()` immediately, call `setSelectingIndex(clamped)` first, `await` (via `setTimeout`, consistent with the rest of the file's timer-based sequencing, not real `async`/`await` against React state) `expandedSelectFadeOutDurationMs` + `expandedSelectReorderDurationMs` + `expandedSelectHoldMs`, *then* proceed with the existing `expandedSelectionRef.current = clamped; setPosition(clamped); closePanel();` sequence unchanged. Reduced-motion collapses this wait to `0` exactly like every other phase.
5. **Promote existing hardcoded constants**: `PANEL_COLLAPSE_TRANSITION_MS` → read `config.panelCollapseDurationMs`; `LIST_SETTLE_EASING`/`LIST_SETTLE_DURATION_S` → `config.selectMotionEasing`/`config.listSettleDurationMs`. Remove the now-dead module-level `const`s (`:24`, `:28-29`).
6. **Timer cleanup**: the new phase-2→4 `setTimeout` needs the same discipline as the existing `settleTimerRef` (clear-on-unmount, clear-on-re-select-before-it-fires) — add a sibling ref (`selectSequenceTimerRef`) rather than reusing `settleTimerRef`, since the two timers now run in sequence, not as alternatives.
7. **Manual verification** (per [[feedback_verify_dont_assume]] — reproduce live, adversarial cases too): open the expanded panel, tap a row roughly in the middle of the list, and confirm (a) unselected rows visibly fade before the panel starts shrinking, not concurrently; (b) the selected row is at the top and the row order below it exactly matches what the collapsed short list shows immediately after; (c) rapid double-tap (select a row, then immediately tap another before phase 2 finishes) doesn't leave stale timers driving two overlapping sequences; (d) `prefers-reduced-motion: reduce` collapses the whole sequence to an instant jump, no fades/reorders visible; (e) tapping the very first or very last row (edge of `computeWindowStart`'s Rule A/B/C boundaries) still produces the correct trailing-row order.

## Decisions needed

1. **Do fading-out rows stay in the DOM (visually behind/interleaved) during the reorder, or get removed from the render list the instant they start fading?** Affects whether `AnimatePresence`'s `exit` prop drives the fade (removed immediately, animates out) or a plain `animate={{opacity:0}}` on a row that stays mounted until phase 2's timer ends. Recommend: `AnimatePresence` `exit`, since Motion's `layout` reorder animation for the surviving rows works more predictably when the exiting siblings are properly registered as exiting rather than just faded in place.
2. **Should the full expanded list truly reorder (Motion `layout` prop, rows sliding past each other), or just fade out the non-surviving rows in place while the surviving rows individually animate to their new slot positions** (equivalent end-state, different visual path — the task says "bring the newly selected article to the top... with a proper transition," which reads as the row itself visibly traveling, favoring `layout`)? Recommend `layout` per the literal ask, flag if a lighter-weight non-traveling version is preferred instead.
