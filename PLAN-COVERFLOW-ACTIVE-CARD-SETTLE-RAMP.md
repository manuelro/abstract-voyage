# Plan: ramp the active card's own proximity sensitivity from 0 to peak over its settle window

**Revision note (2026-09-06, second pass):** operator asked for confirmation that tilt is covered symmetrically with color, and that scale is "treated the same way" as both — and reframed the mechanism as fully symmetric: damp to zero as a card *lands* inactive, ramp back from zero as it *starts* transitioning to active. That reframing exposed a cleaner design than the original one-directional plan (which left the outgoing card on the already-shipped instant-zero taper and only added ramp-*up* for the incoming one) — see "Unified design" below, which replaces that asymmetric approach with one symmetric ramp covering both directions.

**Revision note (2026-09-06, third pass):** operator asked for a config knob exposing the ramp's own change rate, and to resolve this plan's two open decisions rather than leave them open. Resolved: **one symmetric duration**, operator-tunable, governing both directions identically. **`inactiveCardHoverAmplitudeStep` stays** as a safety-net floor, not retired in this pass. Both superseded sections below are updated in place, not left as open questions.

**Revision note (2026-09-06, fourth pass):** operator asked whether the new knob could use the same simple 0–1 range as `inactiveCardHoverAmplitudeStep`, instead of an open-ended millisecond number. Resolved: yes — `activationRampDurationMs` is replaced with `activationRampRate` (0–1, same bounds as its distance-based sibling), converted internally to a real duration via a fixed reference constant, mirroring this same config file's own existing `depthPxAtReferenceWidth`/`referenceWidthPx` ratio-against-a-reference pattern. See "Config knob" below for why a literal "step per millisecond" (the most direct translation of the distance-based field's own shape) doesn't work and what was used instead.

**Revision note (2026-09-06, sixth pass):** operator pushed back on the fifth pass's own gap-closing design: no new boolean values, sensitivity must read as progressive rather than binary, and the gradient side is narrowed to brightness only for now. **Interpretation, stated explicitly since the instruction was terse enough to admit more than one reading:** not an objection to `stackActiveSlide` existing as a fact about a card (that's inherent to CoverFlow's own architecture and can't be designed away), but to the fifth pass's own *implementation shape* — a brand-new `isActive` prop plus a generic tween *object* (`activationRampRef` with its own retarget/direction state, mirroring `runElevationTween`) reads like new on/off switch machinery layered on top of the ramp, even though its output was already continuous. Resolved: drop the new prop and the tween-object framing entirely. Reuse the *already-existing* `stackActiveSlide` value one level further down (not a new boolean), track a single plain timestamp ref updated via the same "compare previous vs. current" idiom `useCardLiftPhysics.ts` already uses for `forceElevated`, and compute progress inline each frame from elapsed time with a plain formula — no tween object, no separate target/direction state. Gradient scope narrowed to `brightnessBoost` alone; `offsetGain`/`hueShiftAmount`/`saturationBoost` are out of scope for this pass and keep today's undamped behavior. Both closed gaps below are rewritten, not left as two competing versions.

## Context

Operator report (screenshot, list-nav driven): while clicking timeline rows to change the active CoverFlow card, the card becoming active shows a live hologram-driven gradient/brightness shift purely from cursor proximity — because the pointer happens to be resting near the list, which sits adjacent to where cards travel. This is visible specifically because the card is still sliding into position (CoverFlow's own position spring hasn't settled) while its proximity response is already at full strength.

This is not a new bug class — it's the still-unaddressed half of `AUDIT-COVERFLOW-PROXIMITY-JUMP.md`'s original diagnosis. That audit's recommendation #3 (the distance-based amplitude taper, `inactiveCardHoverAmplitudeStep`) was implemented and covers the *outgoing* card. Recommendations #1/#2 (a real settle-gated freeze, covering the *incoming* card) were never built. This plan is that missing half, scoped narrowly: ramp the active card's own proximity sensitivity over time, rather than gating on distance (which is always 0 for the active card and thus can't help here).

**Verified against current code before writing this plan** (per `UI-BUG-DIAGNOSIS-PROTOCOL.md` — check known/live values first):
- `hoverAmplitudeMultiplier` (`pages/abstract.tsx:3897-3899`) is `1 - min(1, distanceFromActive * step)` — always `1` for the active card (`distanceFromActive === 0`), confirming it structurally cannot address this.
- `disabled` on both `useCardLiftPhysics` (`AbstractJournalLabCollection.tsx:879`) and the hologram engine's own `usePointerProximity` (`~953`) is gated only by `stackNeighborSettled`, which requires `!isActive` — confirming neither engine has any settle-awareness for the active card today.
- `CoverFlow.tsx:380-392` already computes `settledIndex`/`hasSettled`, a discrete boolean flip `config.activeSettleDelayMs` after an `activeIndex` change — the existing building block this plan extends into a continuous ramp.

## Feasibility: yes

This generalizes the exact pattern already proven twice this session (a 0–1 multiplier scaling `proximityScale`/`proximityLiftPx`/`tiltMaxDegrees`, and — as of the sixth pass, scoped to `brightnessBoost` specifically rather than all four hologram fields — the same multiplier applied to the single most visible, most proximity-affected gradient term) — the only change is the multiplier's *source*: time-since-became-active for the incoming card, instead of distance-from-active for outgoing ones. No new architecture, no new engine — an extension of infrastructure that already exists and already works.

## Unified design — one symmetric activation ramp, not two separate mechanisms

The operator's reframing ("damp to zero as it lands inactive, retake from zero as it starts transitioning to active") is a more elegant model than the original plan's asymmetric one (instant-zero on the way out, ramp on the way in) — and it exposes that **the existing distance-based taper and this new time-based ramp are really the same concept**, just triggered by two different signals (distance vs. time). Proposal: replace them with a single per-card **activation ramp** — one continuous progress value per card, 0 (fully capped) to 1 (full ceiling), that:

- Ramps toward **1** whenever `isActive` becomes `true` for this card.
- Ramps toward **0** whenever `isActive` becomes `false` for this card.
- Uses the same duration and easing in both directions — symmetry is the point.
- Is time-driven only (elapsed since the last activation-state flip), independent of `distanceFromActive` — a card that jumps straight from active to a far neighbor in one list click ramps down over the same fixed duration as a card landing on the adjacent slot, because the ramp is about "how long has this card held its current role," not how far it physically traveled.

This one mechanism, applied identically, is what makes scale, lift, tilt, and brightness "treated the same way" — one progress value multiplied into each wherever it's computed, not several separate treatments checked for parity by hand. (Saturation/hue-shift/pan are out of scope for this pass — see the "Hologram engine" section below for why brightness specifically.)

### Where the ramp should live — not a new React-level per-frame state

Do **not** expose this as a continuous number through `CoverFlowCardReveal`/React props re-rendering every frame — that would force a full CoverFlow re-render at animation-frame rate for the whole ramp window, a real performance cost for a purely cosmetic damping effect. Both proximity engines already run their own continuous per-frame loops independently of React's render cycle (`usePointerProximity`'s module-level `stepFrame`, `GradientRenderer`'s WebGL render loop) — the ramp should be computed *inside* those existing loops, driven by the existing `stackActiveSlide`/`isActive` fact each engine already receives (or, for `GradientRenderer`, needs threaded one level further — see "Hologram engine" below) plus one plain, internally-tracked timestamp of when that value last flipped. No new tween object, no new state machine — a ref holding a number, updated once per flip, read every frame to compute progress inline.

### Lift-physics engine (`useCardLiftPhysics`) — scale, lift, *and* tilt, explicitly

**Revised in the sixth pass** — no dedicated tween object. A plain `roleChangedAtRef` timestamp (updated via a render-time comparison whenever `stackActiveSlide` flips, mirroring the existing `previousForceElevatedRef`/`forceElevatedTransitionPendingRef` idiom already in this file) drives an inline computation: `progress = ease(clamp((now - roleChangedAtRef.current) / effectiveDurationMs, 0, 1))`, then `stackActiveSlide ? progress : 1 - progress`. See Gap 2 (below, "Readiness check") for the one real technical wrinkle this simplification still has to account for: `usePointerProximity`'s own per-frame loop stops ticking once proximity settles, so a minimal, self-terminating `requestAnimationFrame` loop (not a reusable tween utility — just "keep asking for one more frame until progress reaches its target") is still needed to keep this number reaching the screen while the pointer itself is stationary.

Scale and lift are **not** the whole story — `composeAndApply` (`useCardLiftPhysics.ts`) computes them from `elevationPx` via `liftGain`/`scaleGain`, but **tilt is computed on a separate path**, directly from raw `proximity`/`x`/`y` and `config.tiltMaxDegrees`, never touching `elevationPx` at all:
```js
const lift = elevationPx * liftGain;                                   // scale/lift path
const scale = 1 + elevationPx * scaleGain;
const tiltX = ... ? -y * proximity * config.tiltMaxDegrees : 0;         // separate tilt path
const tiltY = ...    x * proximity * config.tiltMaxDegrees : 0;
```
Because these are two independent formulas in the same function, `progress` must be multiplied into **both** — once into the elevation target (or directly into `lift`/`scale`) and once into the tilt computation (equivalent to scaling `config.tiltMaxDegrees` by the same value before it's used). Missing the second one would leave scale/lift correctly damped while tilt kept firing at full strength — exactly the kind of asymmetry being asked to avoid here.

### Hologram engine (`GradientRenderer.tsx`) — brightness only, scoped deliberately

**Scope, decided in the sixth pass:** target `hologramBrightnessBoost` specifically — the single most visible, most proximity-affected term, and the one the operator's own report called out directly. `hologramOffsetX/Y`, `hologramHueShift`, and `hologramSaturationBoost` are **out of scope for this pass** and keep their current, undamped behavior (still driven by `hologramResponseStrength` alone, exactly as today). This is why the ramp is **not** multiplied into the shared `hologramResponseStrength` value itself (`GradientRenderer.tsx:474-496`) — that value feeds all four terms, so damping it would damp all four regardless of intent. Instead, compute the ramp separately and apply it only where `hologramBrightnessBoost` is derived:

```js
// existing line, unchanged:
hologramBrightnessBoost = hologramResponseStrength * hologramConfig.brightnessBoost;
// becomes:
hologramBrightnessBoost = hologramResponseStrength * hologramConfig.brightnessBoost * brightnessRampProgress;
```

`brightnessRampProgress` is computed inline, each frame, from a plain timestamp ref (see "Where the ramp should live" above) — no separate tween object. Concretely: `GradientRenderer` needs `isActive` threaded one level further than it goes today (confirmed via grep: zero references currently — `AbstractJournalLabHueFadeCard` already has `stackActiveSlide`, pass it straight through as a new `isActive` prop on `LiquidGradientAdapter`, the same plumbing shape `hologramDampingAttackMs`/`-ReleaseMs` already use). Internally: a render-time ref comparison (mirroring `useCardLiftPhysics.ts`'s own `previousForceElevatedRef` idiom, not new infrastructure) detects the flip and records `roleChangedAtRef.current = performance.now()`; the existing per-frame loop computes `brightnessRampProgress = ease(clamp((now - roleChangedAtRef.current) / effectiveDurationMs, 0, 1))`, then `isActive ? progress : 1 - progress` for the ramp-down direction. No extra "keep it alive" driver needed here specifically — `GradientRenderer`'s own render loop is already continuously active for both the newly-active card (`meshActivity: 'continuous'` the instant it becomes active) and the outgoing one (stays `'continuous'` for `neighborGradientRevealDurationMs`, ~500ms — comfortably covering the ramp's own ~400–800ms window) per the existing `coverFlowLiveMeshIndices` mesh-performance logic, so the loop is guaranteed to still be ticking through the whole ramp without any new scaffolding to keep it that way.

### Keeping both engines in sync

Since the ramp is computed independently in two files, both must read the *same* `activationRampRate` value (and derive the same effective duration from it) threaded down from the same `coverFlowConfig` (see "Config knob" below) — not two independently-hardcoded numbers that happen to start out equal and could drift apart on the next tuning pass.

### Config knob — `activationRampRate` (new field, `CoverFlowConfig`), 0–1

**Why not a literal "step per millisecond"** (the most direct translation of `inactiveCardHoverAmplitudeStep`'s own shape, `ceiling = 1 - min(1, elapsedMs * step)`): the distance-based field's useful range spans a handful of integer steps (0, 1, 2, 3...), so a 0–1 step size meaningfully covers it. Time doesn't share that scale — a 400ms ramp needs `step ≈ 0.0025`, an 800ms ramp `step ≈ 0.00125`. Every practically useful value would be crammed into the bottom 1% of a 0–1 slider, making it imprecise and unintuitive to tune. A literal unit-for-unit copy of the mechanism doesn't survive the change of axis.

**What does work, and is already this config file's own precedent:** a 0–1 operator-facing dial converted internally to a real millisecond duration via a fixed reference constant — exactly the shape `depthPxAtReferenceWidth`/`referenceWidthPx` already use elsewhere in this same file (`CoverFlow.tsx:277-278`: `depthPx = depthPxAtReferenceWidth * (itemWidth / referenceWidthPx)`, a ratio scaled against a fixed reference point). Applied here:

- **Type/home:** `CoverFlowConfig.activationRampRate: number`, range **0–1** — same bounds as `inactiveCardHoverAmplitudeStep`, living right beside it conceptually (this config file's other "0–1 ceiling multiplier" knob) even though it's grouped with `activeSettleDelayMs` in the "Active card reveal" panel group functionally.
- **Meaning:** `0` = instant, no ramp — byte-identical to today's behavior, matching every other "0 disables this" field's own convention in this file. `1` = maximally gradual.
- **Internal conversion:** a fixed, non-operator-facing constant — `ACTIVATION_RAMP_REFERENCE_DURATION_MS` (proposed 800ms, matching the position spring's own real settle-time upper bound per the original audit's derivation) — with `effectiveDurationMs = activationRampRate * ACTIVATION_RAMP_REFERENCE_DURATION_MS`. Not a panel field itself; a constant in `CoverFlow.config.ts` alongside the field, the same way `HOLOGRAM_MAX_OFFSET_PX`-style fixed multipliers already exist uninterrupted elsewhere in this codebase without being exposed for tuning.
- **Default:** `0.5` — deliberately echoing the *original* (later superseded) default of `inactiveCardHoverAmplitudeStep`, giving `400ms` under the proposed reference constant. A reasonable, familiar starting point to tune live from, not a final answer.
- **Clamp bounds:** 0–1, matching `inactiveCardHoverAmplitudeStep` exactly.
- **Easing:** unchanged from the prior revision — reuse `useCardLiftPhysics`'s existing `ctaConfig.stateExitEasing` token rather than adding a second new field.
- **Plumbing:** unchanged from the prior revision — `pages/abstract.tsx`'s `renderCoverFlowItem` resolves `coverFlowConfig.activationRampRate` into the effective duration and threads it down the same path already used for `hologramDampingAttackMs`/`hologramDampingReleaseMs` (`AbstractJournalLabCollection.tsx`'s existing `LiquidGradientAdapter` call is the precedent), into both the `useCardLiftPhysics` call and the `GradientRenderer` props.
- **Panel field:** `kind: 'number'`, `min: 0`, `max: 1`, `step: 0.01` — matching `inactiveCardHoverAmplitudeStep`'s own panel field shape exactly, not `activeSettleDelayMs`'s ms/integer shape.

### `inactiveCardHoverAmplitudeStep` — kept, not retired, and how it composes with the new ramp

Decided: keep the existing distance-based taper as a safety-net floor. It becomes redundant for the specific transition it was built for (active ↔ immediate neighbor — the new ramp already lands a departing card at 0 over the `activationRampRate`-derived duration, the same end state this field already produces), but it costs nothing to leave in place and provides a hard backstop if the ramp is ever interrupted mid-flight (e.g. a card reactivated before its down-ramp finishes) or a future card ends up several positions from active without passing through a clean ramp-down. Revisit retiring it only after the new ramp has been live and verified for a while — not in the same pass that introduces it.

**Relationship between the two mechanisms — same shape and same 0–1 range, deliberately different axis underneath.** `inactiveCardHoverAmplitudeStep` (currently `1`, confirmed live — not `0.5`, which was its original, later-superseded default) already does exactly this pattern for a *discrete* axis: `hoverAmplitudeMultiplier = 1 - min(1, distanceFromActive * step)`, one number driving a linear, clamped ceiling multiplied into the same target fields on both engines (`pages/abstract.tsx:3897-3921`). `activationRampRate` is the identical mechanism generalized to a *continuous* axis (elapsed ms instead of integer distance steps) — both are 0–1 operator dials with identical bounds and identical "0 disables it" semantics; only the internal conversion differs (distance multiplies directly, time first scales against the fixed `ACTIVATION_RAMP_REFERENCE_DURATION_MS` reference before it's used) because time and distance don't share a natural scale.

**They compose, not compete, for an inactive card:** the time ramp governs the transition window itself (how quickly the ceiling reaches 0 after losing active status); the distance floor is what the ceiling settles into and stays at for as long as the card remains inactive and further than one step away. The active card only ever reads the time ramp — `distanceFromActive === 0` always makes the distance-based multiplier a no-op for it, same as today.

## Readiness check (2026-09-06, fifth pass, revised sixth pass) — two integration gaps found and closed

Asked directly whether this plan was ready for implementation. Checked rather than assumed, per `UI-BUG-DIAGNOSIS-PROTOCOL.md`, and found two real gaps at the code-integration level (the concept and config surface were already solid; these are "how exactly does this wire in" gaps a competent implementer would hit immediately). Gap 1's resolution was superseded by the sixth pass's own brightness-scoping and "no tween object" simplification; Gap 2's finding stands but its resolution was simplified the same way.

### Gap 1 — `GradientRenderer`/`LiquidGradientAdapter` has no activation signal at all

Confirmed via direct grep: zero references to `isActive`/`stackActiveSlide` anywhere in `GradientRenderer.tsx` before this plan. **Superseded by the sixth pass's own "Hologram engine" section above**, which now carries the authoritative version of this resolution (thread the existing `stackActiveSlide` one level further as a plain `isActive` prop, track one timestamp ref, compute progress inline per frame — no tween object) — not repeated here to avoid two sources of truth drifting apart.

### Gap 2 — how the ramp interacts with `useCardLiftPhysics`'s *existing* elevation-tween gating, without a tween object of its own

`applyProximity` (`useCardLiftPhysics.ts:500-513`) already has a guard — `if (elevationTweenRef.current || forceElevated || forceElevatedTransitionPendingRef.current) return;` — that lets a discrete tween (press/focus/release) own the elevation value without a live proximity frame fighting it. **Still true after the sixth pass's simplification:** the ramp must stay fully orthogonal to this gate, not woven into it — multiplying a ramp value onto `composeAndApply`'s already-computed `lift`/`scale`/`tiltX`/`tiltY` output, as the very last step before they're written to `element.style.transform`, sidesteps the question entirely regardless of which existing mechanism produced those values.

**What changed:** no `activationRampRef` tween object with its own retarget/direction state. Just the same shape as the hologram side — a plain `roleChangedAtRef` timestamp, updated via a render-time comparison when `stackActiveSlide` flips, and `progress = ease(clamp((now - roleChangedAtRef.current) / effectiveDurationMs, 0, 1))` computed inline wherever it's needed, then `stackActiveSlide ? progress : 1 - progress`.

**One real constraint that doesn't go away, and is worth being explicit about rather than glossing over:** unlike `GradientRenderer`'s WebGL render loop (continuously alive during the relevant window regardless), `usePointerProximity`'s own per-frame loop stops scheduling frames once proximity settles (`usePointerProximity.ts`: `if (unsettled) scheduleFrame(); else previousFrameTime = 0;`). If the pointer isn't moving while a card ramps, nothing else will keep calling `composeAndApply` to reflect the changing ramp value — the number would update in the ref but never reach the screen. This isn't solvable by "just compute it inline" alone; *something* has to keep asking for one more frame while `progress < 1`. The minimal version of that — not a generic tween utility, just a self-terminating `requestAnimationFrame` loop that stops the instant `progress` reaches its target — is still necessary here specifically, for this specific technical reason, not because ramps in general need one.

## Revision note (2026-09-08, eighth pass) — the real reason the boost still fires: a stale-rect bug in `usePointerProximity` itself, not the ramp

Operator report (second screenshot, same repro): after the seventh-pass widening shipped, the reported effect *still* appears. Verified live before writing anything further (per `UI-BUG-DIAGNOSIS-PROTOCOL.md`) — this time instrumenting `useCardLiftPhysics.ts`'s own `composeAndApply` directly rather than trusting output alone.

**Finding: `activationRampCeiling` is provably correct.** Direct instrumentation showed it resolving to exactly `1` right on schedule (elapsed ≫ `activationRampDurationMs`, verified numerically) for the newly-active card, and `0` for the newly-inactive one, in every sample taken. The ramp itself has no bug.

**The actual defect is upstream, in the shared `components/proximity/usePointerProximity.ts` module `useCardLiftPhysics`/`GradientRenderer` both subscribe to — and it only surfaces when the cursor is *stationary* while a card's own box is still being carried into place by CoverFlow's position spring** (i.e., exactly the reported repro: cursor resting near the list, not actively moving, while a list-nav click triggers the slide):

- `stepFrame` (`usePointerProximity.ts:100-170`) only re-measures a subscriber's `getBoundingClientRect()` when the pointer is "active" *and* >160ms has elapsed since the last measurement (`:114-120`) — a real pointer-move event is what re-triggers this, not the element's own CSS-transform position changing.
- Once the damped `current` value catches up to whatever `target` was computed against the *most recent* rect snapshot, the module-level loop marks itself settled and **stops scheduling further frames** (`:168-169`: `if (unsettled) scheduleFrame(); else previousFrameTime = 0;`).
- If the cursor stops moving while the card's box is *still* sliding (CoverFlow's own spring, entirely outside this module's awareness — no resize/scroll/intersection event fires from a transform on an ancestor), the engine can lock in a `proximity` value computed against the card's box at some **intermediate, not-yet-final position**, then never recompute it again — nothing left to restart the loop until the next real pointer-move.
- Confirmed by direct measurement: with the cursor placed once at a fixed point and never moved again, `proximity` for the newly-active card sat at a value corresponding to the card's box *before* it finished sliding (`0.1129`, unchanging across three samples 80ms apart — the signature of a dead loop, not a still-decaying one) — while the *same* card, if already active and settled *before* the cursor ever moved there, correctly read `0.6188` from the identical final position. Same geometry, same radius, same ramp ceiling (`1` in both cases) — only the mid-transition freeze differs.
- The activation ramp multiplies whatever `proximity` it's handed. A correct ceiling can't fix an already-wrong, frozen input.

**This is exactly the gap the very first pass of this plan named and deliberately left out of scope:** *"Not a fix for `AUDIT-COVERFLOW-PROXIMITY-JUMP.md`'s original root cause (the missing `stackSlotAnimating`/`freeze` wiring, and the disable gate riding an unrelated mesh-timer instead of real position-settle)."* Both proximity engines already support a `freeze` option built for precisely this ("an element whose own bounding box is being animated elsewhere... holds whatever proximity/position was last computed... instead of computing fresh, misleading data against a moving box") — `SplitColumnCardPreview`'s own `CardStackSlot` already wires this from `stackSlotAnimating`. **CoverFlow's own `renderCoverFlowItem` (`pages/abstract.tsx`) never passes `stackSlotAnimating` to `AbstractJournalLabHueFadeCard` at all** — the wiring simply doesn't exist for this component, so neither proximity engine has ever had freeze protection during CoverFlow's own position-spring window, ramp or no ramp.

**Not implemented this pass (analysis only, per operator request).** The fix this points to: surface CoverFlow's own "this card's position is still mid-transition" signal (CoverFlow.tsx doesn't currently expose one at the per-card level — `reveal.hasSettled` is the closest existing concept, but it's keyed to the *active* index globally via `activeSettleDelayMs`, not per-card "is this specific card's box still animating") and thread it as `freeze` into both `useCardLiftPhysics` and the hologram's own `usePointerProximity` call, the same pattern already proven in the other stack. This is a different, complementary mechanism from the ramp: the ramp controls *how loud* the effect is allowed to be once the signal is trustworthy; `freeze` controls *whether the signal is trustworthy at all* during the window the box is moving under something other than the pointer.

## Revision note (2026-09-08, ninth pass) — implemented: `livelyUntilMs`, not `freeze` — the underlying signal stays continuously live, not held still

Operator pushed back on the eighth pass's own `freeze` recommendation: the entire point of the ramp is a continuously interactive, high-quality transition at all times — a binary `freeze`→release would read as two visibly distinct stages (held still, then suddenly live), exactly the discontinuity the ramp exists to avoid. Instructed to reassess: whatever is causing the residual issue must be folded into the *existing* progressive ramp (`activationRampRate`/`activationRampDurationMs`), not a new binary mechanism.

**Reassessed design — same window, opposite response from `freeze`.** `freeze` (already in both engines) holds the last computed value still and skips re-measurement entirely, for a scenario where accepting a fresh-but-misleading read is worse than accepting a stale one. This needed the opposite response for the identical trigger (a box moving under something other than the pointer): stay maximally *live* — re-measure and re-compute every frame — for exactly as long as the box might still be moving, so the signal itself never has a chance to go stale in the first place. No two-stage read: the ramp's own amplitude ceiling keeps rising smoothly the entire time, now multiplying an always-accurate, continuously-updating proximity instead of a snapshot that could freeze at whatever it happened to be mid-slide.

**Implemented — one new opt-in option on the shared `usePointerProximity` module, reusing the ramp's own duration, no new config knob:**

- `usePointerProximity.ts`: new `livelyUntilMs?: number` option (default `0`, inert for every existing caller — `performance.now()` is always positive) — an *absolute* deadline, not a duration, so the caller computes it once per role-change (`roleChangedAt + activationRampDurationMs`) rather than re-deriving "how much longer" every render. While `performance.now() < livelyUntilMs` for a subscriber: its rect is re-measured on every frame (bypassing the normal >160ms throttle), and it alone keeps the shared per-frame loop scheduling (bypassing the normal "stop once every subscriber's damped value has caught up" idle check) — closing both halves of the eighth pass's diagnosis (stale rect *and* the loop going idle against it) without ever holding output still.
- `useCardLiftPhysics.ts`: its own internal `usePointerProximity` call now passes `livelyUntilMs: activationRampRoleChangedAtRef.current + activationRampDurationMs` (using the *same* ref/duration already driving the ceiling — no second timer).
- `AbstractJournalLabCollection.tsx`: the hologram engine's own separate `usePointerProximity` call needed its own copy of the "when did `stackActiveSlide` last flip" bookkeeping (encapsulated inside `useCardLiftPhysics`, not reachable from here) — added `hologramRoleChangedAtRef`, same render-time flip-detection idiom, driving the same `livelyUntilMs` shape for this subscription.

**Verified live**, using a corrected repro methodology (the eighth pass's own instrumentation had been fooled by Playwright's `locator.click()`, which silently re-hovers the mouse to the clicked element's own center before clicking — every earlier "stuck" measurement was reading the *real* proximity for wherever the mouse ended up after that hidden move, not a stale value; switched to a JS-dispatched `el.click()`, which fires the same handler without moving the cursor, to get a faithful "cursor never moves" test):
- With the cursor genuinely stationary throughout, `proximity` now tracks the sliding card's rect continuously (`1418→1132→865→819→804→793.6`, matching the box's own real position at every sample) and converges smoothly to `0.616` — matching a settled-and-hovered baseline from the identical final position almost exactly (`0.6188`) — with no discontinuity at the point the `livelyUntilMs` window closes.
- Resulting rendered scale at the same fixed point: `1.01172` vs. a `1.01184` settled baseline — correct, not stale.
- Hologram color at the real list-row distance: muted at t~100ms (`[30,29,48]`), smoothly rising, converging to a single stable value by t~700ms and holding steady through 2.5s+ — no stuck/wrong plateau.

This closes the actual reported bug: the ramp's own amplitude curve was already correct; the signal it multiplied is now correct too, continuously, without introducing any freeze/release seam.

`GradientRenderer.tsx`'s per-frame hologram block (`~505-577`) derives five fields from one shared envelope, `hologramResponseStrength` (the proximity attack/release curve, `stepPointerProximityEnvelope` with `hologramDampingAttackMs`/`-ReleaseMs` — climbs to full strength in ~85ms by default, purely because the card sits near the cursor, entirely independent of whether *this card's own* activation transition has finished):

- `hologramBrightnessBoost` — **ramped** (multiplied by `brightnessRampProgress`, the sixth pass's own addition). Confirmed working via live testing during that pass.
- `hologramOffsetX` / `hologramOffsetY` — **not ramped**. Feeds directly into the gradient field's own position uniform (`helpers/webgl.ts:358-359`: `(paletteOffsetX ?? slide.offsetX) - (motionValues.gradientX + hologramOffsetX) * displacementScale`, same for Y) — this literal pan of the field *is* what reads as "the gradient mesh shifting," the operator's own words in the annotation.
- `hologramHueShift` — **not ramped**. Feeds `uHueOffset` (`webgl.ts:361`), a global hue rotation of the whole rendered field — this is what produces the rainbow/multi-hue spread in the screenshot; the card's resting palette is normally a narrow hue band, not this spread.
- `hologramSaturationBoost` — **not ramped**. Feeds `uSaturation` (`webgl.ts:344`), compounding the vividness alongside the hue shift.

The sixth pass's own "Hologram engine" section says this outright: *"Gradient scope narrowed to `brightnessBoost` alone... `hologramOffsetX/Y`, `hologramHueShift`, and `hologramSaturationBoost` are out of scope for this pass and keep today's undamped behavior."* That sentence is the exact gap the screenshot is now surfacing — brightness genuinely ramps; the other three don't, and they happen to be the more visually dominant terms for a rainbow-gradient card (a hue/position shift reads far more dramatically than a brightness change on this particular gradient treatment).

**Secondary, structural contributor (context, not a new finding):** the hologram engine's own second `usePointerProximity` subscription (`AbstractJournalLabCollection.tsx:948-963`, feeding `interactionRef`/`hologramInteraction`) is disabled only via `stackNeighborSettled`, which requires `!isActive` — so for the newly-active card this subscription is *never* disabled, live from the instant it becomes active. This is the same structural gap the original audit identified for the lift-physics engine before any ramp existed; the sixth pass's ramp works *downstream* of this (damping the derived value, not gating the subscription itself), same approach already proven for brightness.

**What closing this would take, conceptually (not implemented this pass):** the exact same ramp value already computed once per frame in that block (today named `brightnessRampProgress`, would need a scope-neutral rename, e.g. `hologramRampProgress`) multiplied into `hologramOffsetX`, `hologramOffsetY`, and `hologramHueShift`/`hologramSaturationBoost` identically to how it's already multiplied into `hologramBrightnessBoost` — no new mechanism, no new config knob (`activationRampRate`/`activationRampDurationMs` already cover it), just widening which of the five derived fields the existing multiplier reaches. The open question for a future pass: whether to ramp all four remaining fields together (fully symmetric with lift-physics' "no field left behind" framing) or stage them (e.g. offset/hue first, since those are what the screenshot calls out, saturation after) — this plan doesn't resolve that here since no implementation was requested.

## Plan (2026-09-08, tenth pass) — bring `hologramResponseStrength` and the ambient sweep's own tilt under the same damping — IMPLEMENTED

Per the most recent proximity-effects audit, two things still sat outside the ramp: the shared `hologramResponseStrength` envelope itself (the four derived hologram terms were ramped individually, but the envelope they're all derived from wasn't — harmless only because every existing reader multiplied it by something already-ramped or ignored it entirely), and the ambient sweep's own tilt write, a parallel path that never touched the ramp at all. Both closed, following the same "one continuous multiplier, applied to the existing formula, no new mechanism" template the rest of this document already establishes.

**Implemented as planned, both parts:**
1. `GradientRenderer.tsx` — `hologramRampProgress` is now multiplied into `hologramResponseStrength` once (`hologramResponseStrength *= hologramRampProgress`), immediately after `hologramStrengthRef.current` is updated (so the *stored* attack/release envelope stays the real, undamped signal for next frame's own stepping — only this frame's output variable is damped). The four derived terms simplified back to reading `hologramResponseStrength` plain, dropping their individual `* hologramRampProgress`. `outputTreatmentInteractionStrength` needed no code change — it inherits the damped value automatically.
2. `AbstractJournalLabCollection.tsx` — the ambient sweep's `onFrame` callback now computes an inline ramp ceiling (reusing the existing `hologramRoleChangedAtRef`/`activationRampDurationMs`/`ctaConfig.stateExitEasing`, cached via a new `ambientSweepRampEasingCacheRef`) and multiplies it into both `--reveal-tilt-x`/`-y` writes. No directional branch needed — confirmed the containing effect only ever runs once `stackActiveSlide` is already true.

**Verified:** `tsc` clean. Live regression check (cranked hologram config, list-adjacent cursor, real list-nav click) reproduced the exact same muted→converged curve as the ninth-pass verification (`t~100ms` muted, smooth rise, stable by `~700ms-1.3s`, holding steady after) — confirming the centralization changed *how* the number is computed, not the number itself. Lift/scale side re-verified unaffected (`1.01172` vs. `1.01184` settled baseline, matching prior runs).

### 1. Centralize the ramp onto `hologramResponseStrength` itself (`GradientRenderer.tsx`)

**Current shape** (`~547-595`): `hologramResponseStrength` is computed once (attack/release envelope, real proximity), then each of the four derived terms independently multiplies it by `hologramConfig.<field>` *and* `hologramRampProgress` separately — four repeated `* hologramRampProgress` multiplications of the same undamped envelope. `outputTreatmentInteractionStrength` (`~708`, metal-luminance mode only, not read by CoverFlow's own color-mode cards but shared by other `LiquidGradientAdapter` callers) reads the *raw*, still-undamped `hologramResponseStrength` directly — the one place today where a value that should read as "this card is transitioning" doesn't.

**Planned change:** compute `hologramRampProgress` (unchanged formula), then apply it to `hologramResponseStrength` itself, once, in place — `hologramResponseStrength *= hologramRampProgress;` — immediately *after* `hologramStrengthRef.current` has already been updated with the real, undamped attack/release step (so the ref's own internal state, which the *next* frame's attack/release stepping reads from, stays the true, unramped signal — only the local variable used for *this frame's output* gets damped). Then simplify all four derived terms back to reading `hologramResponseStrength` plain, with no separate `* hologramRampProgress` — since it's already baked in. `outputTreatmentInteractionStrength: hologramResponseStrength` (`~708`) needs no code change at all; it automatically starts reading the damped value once the variable itself carries it.

**Why this is safe for every other `LiquidGradientAdapter` caller** (ScatterCard, DeckSwiper, DeckPager, View.tsx, the two-face flip card, metal-luminance labs): all of them leave `activationRampDurationMs` at its default (`0`, never passed), which already makes `hologramRampProgress` resolve to `1` unconditionally — multiplying by `1` is a no-op. Only CoverFlow's own cards (the sole caller that threads a nonzero `activationRampDurationMs`) are affected.

### 2. Damp the ambient sweep's own tilt write (`AbstractJournalLabCollection.tsx`)

**Current shape** (`~1236-1257`): `runHologramExciteSweep` writes its synthetic proximity/x/y into the *same* `interactionRef` real cursor proximity uses — so once change (1) above ships, the sweep's own contribution to the four hologram terms is **already covered automatically** (it's just another input feeding the same, now-damped `hologramResponseStrength` pipeline; no separate work needed there). What isn't covered: the sweep's `onFrame` callback *also* writes `--reveal-tilt-x`/`--reveal-tilt-y` CSS custom properties directly (`~1255-1256`), a third, independent tilt path that never touches `useCardLiftPhysics`'s own ramped `tiltX`/`tiltY` at all, and multiplies `ambientTiltMaxDegrees` by raw `proximity`/`x`/`y` alone.

**Planned change:** reuse the `hologramRoleChangedAtRef` already added in the ninth pass (tracks the identical "when did `stackActiveSlide` last flip" moment, already sitting in this same component, already driving this same subscription's `livelyUntilMs`) to compute one more inline ramp value inside `onFrame`, using the same `activationRampDurationMs` prop and the same `CTA_BUTTON_MOTION_EASINGS[ctaConfig.stateExitEasing]` token the other two engines already standardize on — then multiply it into both tilt writes:
```js
onFrame: tiltElement ? ({ progress, proximity, x, y }) => {
  const maxDeg = journalHologramConfig.ambientTiltMaxDegrees;
  if (progress >= 1) { /* unchanged cleanup */ return; }
  let rampCeiling = 1;
  if (activationRampDurationMs > 0) {
    const elapsed = performance.now() - hologramRoleChangedAtRef.current;
    const eased = ease(clamp(elapsed / activationRampDurationMs, 0, 1)); // same easing token
    rampCeiling = eased; // no `stackActiveSlide ? … : …` needed — see below
  }
  tiltElement.style.setProperty('--reveal-tilt-x', `${(-y * proximity * maxDeg * rampCeiling).toFixed(3)}deg`);
  tiltElement.style.setProperty('--reveal-tilt-y', `${(x * proximity * maxDeg * rampCeiling).toFixed(3)}deg`);
} : undefined,
```
No `activationRampActive ? eased : 1 - eased` branch is needed here (unlike the other two consumers): the sweep's own containing effect already bails out unconditionally unless `stackActiveSlide` is true, so this callback structurally only ever runs for a card that's active or becoming active — the "receding" half of the ramp is unreachable for this specific consumer, not a gap.

**Interaction with the sweep's own envelope, worth naming rather than treating as a conflict:** the sweep already has its own independent 0→1→0 amplitude curve (`envelopeShape`/`easingCss`, gaussian by default) layered on top of its own `startMs`/`durationMs` schedule. Multiplying the activation-ramp ceiling in as well means the visible tilt is the *product* of two independently-rising curves for whatever window they overlap — strictly gentler than either alone, never a conflict, consistent with "nothing should reach full strength before the transition genuinely resolves."

**Mount-time correctness, verified against the existing convention:** `hologramRoleChangedAtRef` seeds at `Number.NEGATIVE_INFINITY` (ninth pass) — for a card that mounts *already* active (e.g. the page's initial active index, no real flip ever observed), `elapsed` resolves to `Infinity`, `eased` clamps to `1`, and the sweep plays at full, undamped strength immediately — correct, matching every other consumer's "ramp only applies to a real transition, never to initial mount" rule already established throughout this plan.
