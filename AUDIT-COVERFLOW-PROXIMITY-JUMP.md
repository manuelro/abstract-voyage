# Audit: CoverFlow active→neighbor hover/proximity "jump" on list-driven navigation

Scope requested: `experiences/abstract/components/CoverFlow/CoverFlow.config.ts` (as requested), traced out to its actual dependency chain — that file itself owns geometry/timing knobs only and contains **zero** hover/proximity fields (confirmed against `CoverFlow.panel.ts`, which exposes every field in the config type and has no proximity-related group). The defect lives in how `pages/abstract.tsx` wires CoverFlow's cards into the shared cursor-proximity hover engine (`components/proximity/useCardLiftPhysics.ts`), a mechanism this exact codebase already fixed for its *other* carousel (the vertical `CardStack`) but never ported to CoverFlow. Read-only audit; no code changed.

## 0. Symptom, as reported

Desktop `/abstract`: narrow column holds the hero text + `AboutTimeline` list; wide column holds `CoverFlow`, side-by-side (`pages/abstract.tsx:4481-4653`). Clicking a list row jumps the active article. The card that *was* active slides out to a neighbor/edge slot. If the pointer is still near that card as it arrives, its hover-driven scale/lift/tilt visibly snaps instead of settling smoothly — reproduced specifically via **list-driven** navigation, not clicking a neighbor card directly in the carousel itself.

## 1. Two independently-transformed layers on the same card

Every CoverFlow card is two nested transforms, driven by two completely separate systems that know nothing about each other:

1. **Position** — `CoverFlowItemInner`'s outer `motion.div` (`CoverFlow.tsx:687-701`) applies `x`/`z`/`rotateY`, all derived from one shared `scrollX` motion value run through `useSpring(scrollX, { stiffness: 150, damping: 30, mass: 1 })` (`CoverFlow.tsx:333-334`). A list click calls `handleTimelineActiveIndexChange` → `setArticleActiveIndex` → new `activeIndex` prop → CoverFlow's own effect (`CoverFlow.tsx:432-438`) does `scrollX.set(clamped)`, and the spring animates every card's `x/z/rotateY` toward the new layout.
2. **Hover physics** — `useCardLiftPhysics` (`components/proximity/useCardLiftPhysics.ts`), called per-card inside `AbstractJournalLabHueFadeCard` (`AbstractJournalLabCollection.tsx:842-936`), imperatively writes `scale()/translate3d()/rotateX/rotateY` onto an *inner* element (`styles.physics`, the `liftRef` div) based on live cursor distance to that element's own `getBoundingClientRect()`.

These compose visually. Nothing today makes them agree on when the transition is "over."

## 2. `useCardLiftPhysics` already has the exact mechanism this needs — CoverFlow just never feeds it

This codebase hit this identical failure mode before, on the *other* carousel:

- `AbstractJournalLabHueFadeCard`'s `stackSlotAnimating` prop doc comment (`AbstractJournalLabCollection.tsx:619-637`) describes, verbatim, "Round 13"/"Round 14" of a bug where `CardStack.tsx`'s vertical stack produced "an erratic, non-monotonic tilt swing as the box moved into position" because proximity kept computing live against a card's bounding box while that box was itself being translated by scripted stack motion. The fix was `freeze` — passed to both `useCardLiftPhysics` (`AbstractJournalLabCollection.tsx:915`) and `usePointerProximity` (`AbstractJournalLabCollection.tsx:944`) — which holds the current lift/tilt/scale exactly in place and skips proximity recomputation entirely while true (`usePointerProximity.ts:113`: `if (options.freeze) return;`, before the subscriber's rect is even re-measured).
- `CardStack.tsx` computes `stackSlotAnimating` from its own real `step.isTransitioning` state and passes it in. **`pages/abstract.tsx`'s `renderCoverFlowItem` (the CoverFlow render callback, `pages/abstract.tsx:3822-3942`) never passes `stackSlotAnimating` at all** — it defaults to `false` (`HueFadeCardProps`), so CoverFlow cards never freeze. Grep-confirmed repo-wide: no root-level `PLAN-*`/`AUDIT-*`/`BUG-REPORT-*.md` documents this gap or an intentional decision against porting it.

This is a structural gap, not just a missed prop: `CoverFlow.tsx`'s `renderItem` contract (`CoverFlowRenderItem<T>`, `CoverFlow.tsx:115-122`) gives a renderer `isActive` (flips the instant `activeIndex` changes, `CoverFlow.tsx:587`) and `distanceFromActive` (`Math.abs(index - activeIndex)`, `CoverFlow.tsx:711`) — both computed from the *target* index, not from where the spring visually is. There is no equivalent of CardStack's `step.isTransitioning` for CoverFlow today. The only settle-tracking CoverFlow does (`settledIndex`/`hasSettled`, `CoverFlow.tsx:380-392`, gated by `config.activeSettleDelayMs`) describes "has the *new* active card settled," not "has the card that just left settle at its new resting slot" — the exact signal this bug needs and that doesn't exist.

## 3. What actually gates the outgoing card's hover disable today, and why it's decoupled from position

`renderCoverFlowItem` passes `stackNeighborSettled={!isActive && !isMeshLive}` (`pages/abstract.tsx:3925`), which drives `useCardLiftPhysics`'s `disabled` (`AbstractJournalLabCollection.tsx:868`: `!isVisible || !shellVisible || stackNeighborSettled || !hasHoverPointer`). `isMeshLive` (`pages/abstract.tsx:3836`) comes from a `Set` maintained by a *mesh-performance* state machine (`pages/abstract.tsx:3753-3786`): the outgoing card's index is removed from that set — and only then does hover physics start to disable/release — via a plain `setTimeout(..., coverFlowGradientRevealDurationMs)` fired the instant the index changes.

- `coverFlowGradientRevealDurationMs` resolves to `cardAppearanceConfig.neighborGradientRevealDurationMs` (`pages/abstract.tsx:3725-3727`), whose actual default is **500ms** (`SplitColumnCardPreview/config/stack.ts:587`, `Card/config/appearance.ts:54-55` inherits it unchanged). This value was tuned for the neighbor's gradient-mesh cover cross-fade — a rendering-cost concern — and has no structural relationship to card position.
- The position spring (`stiffness: 150, damping: 30, mass: 1`) is overdamped (damping ratio ζ ≈ 1.22 — no oscillation). Its slower pole is ≈ −6.3 rad/s, i.e. a ≈158ms time constant, putting a visual settle somewhere in the **~450–800ms** range depending on where "settled" is drawn. For a linear spring this settle *time* is independent of travel distance — so a list click landing far away (see §4) travels farther in the *same* window, not a longer one.
- `CoverFlowConfig.activeSettleDelayMs` (`CoverFlow.config.ts:164`, default **120ms**) looks like the natural existing knob for "how long until the transition is visually done," but it isn't used for this at all today — it only gates the *new* active card's own content-reveal stagger (`CoverFlow.tsx:383-391`), and by its own doc comment (`CoverFlow.config.ts:84-94`) is already a known-rough approximation, well short of the spring's real settle time.

Net effect: the outgoing card's hover engine stays fully live (not frozen, not disabled) for a fixed 500ms clock that has nothing to do with the spring, while the spring itself is animating that same card's box over a physically-independent ~450-800ms clock. They're close enough in magnitude to often *look* coordinated, which is almost certainly why this reads as a subtle/intermittent bug rather than an obvious one.

## 4. Why this reproduces via the list specifically, not neighbor-card clicks

`AboutTimeline`'s row click passes that row's own absolute `slideIndex` straight through (`AboutTimeline.tsx:356`; `handleTimelineActiveIndexChange`, `pages/abstract.tsx:3612-3616`, does no adjacency clamping) — a click can jump the active index by any number of positions, unlike CoverFlow's own click-to-snap (`CoverFlow.tsx:489-498`) or keyboard arrow nav (`AboutTimeline.tsx:255-270`, clamped to ±1). A farther jump means the outgoing card travels a longer pixel distance in the same fixed settle-time window (§3) at higher velocity, and — critically — the list sits physically adjacent to the CoverFlow's own left edge in this layout (`pages/abstract.tsx:4481-4653`), so the pointer that just clicked a row is already resting exactly where an outgoing/incoming card's bounding box is passing through. That combination (larger, faster in-flight box + pointer already parked in its path) is what surfaces the live-proximity-during-flight defect in §2-3; a same-carousel click rarely leaves the pointer sitting in the outgoing card's flight path the same way.

Compounding this: `usePointerProximity`'s own rect cache only re-measures `getBoundingClientRect()` at most every 160ms while the pointer is active (`usePointerProximity.ts:114-120`). Across a ~500-800ms flight that's only 3-5 samples of a box that has moved substantially between each one — a stale-rect distance computation feeding straight into `resolvePointerProximity` → `composeAndApply`'s `scale()/translate3d()` every one of those frames, with no smoothing against the box's own motion. This is the direct mechanical cause of a *swing*, not just a lagging release.

## 5. Root cause, precisely

CoverFlow reuses `useCardLiftPhysics`'s proximity/hover engine per-card but was never wired to that engine's own `freeze` protection — the exact protection this codebase already built and shipped for `CardStack`'s structurally identical problem. In its absence, an outgoing CoverFlow card's hover/tilt/scale stays fully live against its own physically-animating, staleness-cached bounding box for a ~500ms window whose duration is borrowed from an unrelated mesh-performance concern, not from CoverFlow's own position-settle timing — and even once that window ends, its release is a separate, uncoordinated tween. List navigation exposes this reliably because it removes CoverFlow's own click-to-snap adjacency limit and places the pointer where the animating card's path already is.

## 6. Recommendations

Ranked by how directly each addresses the root cause; per this repo's own stated convention, extending an existing knob before adding a parallel one.

1. **Wire the existing `freeze` mechanism into CoverFlow (primary fix).** `useCardLiftPhysics`/`usePointerProximity` already do everything needed (§2) — the gap is purely that CoverFlow never computes or passes an equivalent of CardStack's `step.isTransitioning`. Concretely: extend `CoverFlow.tsx`'s existing settle-tracking (`settledIndex`/`hasSettled`, `CoverFlow.tsx:380-392` — already the right shape: an effect keyed on `activeIndex` changes with a config-driven timer) to also track the *previous* active index and expose "this index is still mid-flight" through the render contract (e.g. a new field alongside `position.distanceFromActive`, `CoverFlow.tsx:115-122`/`710-712`). `renderCoverFlowItem` (`pages/abstract.tsx:3822`) then passes that straight through as `stackSlotAnimating` — finally activating a path that is fully built and already proven correct for CardStack, not new engineering.
   - This is the one recommendation that actually requires touching files outside the requested `CoverFlow.config.ts` scope (`CoverFlow.tsx` for the tracking/signal, `pages/abstract.tsx` for wiring) — flagging that explicitly since the config file alone has no hook to carry a timing fix; it would only gain the *value* this reuses (see next point).
   - Reuse `activeSettleDelayMs` as that timer's source rather than inventing a second one, but raise its default from 120ms toward the ~500-800ms order of magnitude the spring actually needs (§3) if it's going to gate a real freeze window — 120ms is calibrated for content-reveal pacing, not physical settle, and a freeze that lifts before the spring is actually done reintroduces the same stale-rect swing this is meant to prevent.

2. **Replace (or align) the `isMeshLive`/`neighborGradientRevealDurationMs`-driven disable gate (`pages/abstract.tsx:3925`) with the same settle signal from #1**, instead of the current mesh-performance timer that happens to be roughly the same order of magnitude by coincidence. This removes the accidental near-cancellation masking the bug under short/adjacent transitions and only fully surfacing on longer, list-driven jumps (§4).

3. **Complementary, not a substitute — taper hover amplitude with `distanceFromActive`.** The operator's own idea ("progressively decreasing the scaling change on hover... to a value that keeps the card at final scaling") is directly expressible today: scale `ctaConfig.proximityScale`/`proximityLiftPx`/`tiltMaxDegrees` down as `position.distanceFromActive` grows past 1, before handing that per-card config into `useCardLiftPhysics` (`AbstractJournalLabCollection.tsx:842-843`). This reduces how visible any residual timing seam is (a smaller hover ceiling has less room to visibly snap) but doesn't remove the stale-rect-during-flight mechanism in §4 — recommend pairing with #1, not using it alone.

None of this is safely doable as a `CoverFlow.config.ts`-only change: the file has no proximity/settle-signal surface today (confirmed against `CoverFlow.panel.ts`), and the actual defect is the missing `freeze` wiring between `CoverFlow.tsx`, `pages/abstract.tsx`, and the already-existing `useCardLiftPhysics` engine.
