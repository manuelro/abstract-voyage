# Draggable, persisted, better-animated config panel

## Context

The global developer/design config panel (`components/Panel/`, the "ABSTRACT SETTINGS" floating shell used across every page to live-tune config) is currently pinned to a fixed bottom-right corner with no way to reposition it, has non-configurable expand/collapse timing, gives no visual feedback while an operator is manipulating it, and has a confirmed layout bug: a large dead-space gap renders inside an expanded section's body (see the user's screenshot — a red-outlined empty region below "WORDMARK" spanning most of the panel's height). This plan makes the panel draggable with persisted position, adds configurable elastic/spring-like drag motion, configurable expand/collapse easing, a transparency cue while dragging, dimming for collapsed sections, hover-intent auto-expand, and fixes the dead-space bug — all new behavior exposed as fields on the panel's own existing self-referential config (`PanelShellConfig`, visible in the panel itself as the "CONFIG PANEL" section), not a separate mechanism.

**Every "configurable" requirement in the user's ask means: a new field on `PanelShellConfig`** (`components/Panel/config/shell.ts`), registered as a UI control in `components/Panel/config/shell.panel.ts`, following that file's existing flat-field pattern exactly (no mobile/Wide/Lg tiers — confirmed absent from this config; every field there is global).

## Findings that shape the approach (reuse over reinvention)

- **Positioning today**: `.panelFrame` (`components/Panel/Panel.module.css:59-70`) is `position: fixed`, anchored via `right`/`bottom` + safe-area insets, no `transform`, no existing drag state anywhere in the codebase for this component.
- **Section expand/collapse today**: pure CSS, no JS measurement — `.sectionDisclosure` animates `grid-template-rows: 0fr → 1fr` (`Panel.module.css:693-720`), duration/easing hardcoded as CSS custom properties (`--panel-motion-disclosure: 320ms`, `--panel-motion-disclosure-close: 240ms`, `--panel-easing: cubic-bezier(0.16, 1, 0.3, 1)`, `Panel.module.css:52-56`). **This cubic-bezier is byte-identical to `CTA_BUTTON_MOTION_EASINGS.viscous`** (`components/CtaButton/config/registered.ts:264`) — the shared easing vocabulary already used everywhere else in this codebase (`AbstractPostDockEasingPreset`, `CtaButtonMotionEasing`). Making disclosure timing configurable should reuse `CtaButtonMotionEasing`/`CTA_BUTTON_MOTION_EASINGS`, not invent a new easing enum — zero visual change on migration since the current hardcoded value already matches `'viscous'` exactly.
- **The panel already overrides its own CSS custom properties per-instance**: `PanelShell`'s `shellStyle` object (`components/Panel/index.tsx:666-704`) sets `--panel-radius`, `--panel-backdrop-blur-px`, etc. inline from `panelConfig` fields, which naturally wins over the CSS-class-level fallback. Adding `--panel-motion-disclosure`, `--panel-motion-disclosure-close`, `--panel-easing`, and new `--panel-drag-*` variables to this same object is the established, minimal-footprint way to make CSS timing configurable — no new plumbing.
- **Persistence pattern to replicate exactly**: `components/Panel/config/useConfigScopeOpenState.ts` — module-level cache + `localStorage` (try/catch-guarded) + `useSyncExternalStore`, keyed `'panel-config-open-scopes'`. A new `usePanelPosition()` hook should mirror this file almost verbatim, keyed e.g. `'panel-shell-position'`, storing `{ x: number; y: number } | null`.
- **Reusable spring/drag math**: `components/proximity/useCardLiftPhysics.ts` has real damped-spring settle constants (`SPRING_SETTLE_DISPLACEMENT_PX`, `SPRING_SETTLE_VELOCITY_PX_PER_S`, `SPRING_MAX_STEP_SECONDS`, `SPRING_MAX_DURATION_MS`) and `helpers/cubicBezierEasing.ts`'s `createCssEasingFunction()` evaluates any `CtaButtonMotionEasing` preset as a callable curve. Drag *while held* is a direct 1:1 pointer-follow (no easing needed); the "elastic" quality applies to the **settle transition** — snapping to the final position on release and animating to the persisted position on load. That settle should be a CSS `transition` using a configurable `CtaButtonMotionEasing` + duration (reusing the exact same idiom as disclosure timing), not a full physics simulation — simpler, consistent with the rest of this config, and already proven smooth for CSS transform transitions elsewhere in the app. `'expressive'` (`cubic-bezier(0.22, 1, 0.36, 1)`, overshoot-capable) is the closest existing preset to "elastic" and is a sensible default.
- **Drag handle target**: the user's "top section of the main config panel" is `.panelHeader` (`components/Panel/index.tsx:764-778`), which contains the `.panelTitle` button (click = collapse) and `.headerActions` (COPY ALL / COPY DIFF / RESET buttons). The drag handler must attach to `.panelHeader` itself, not the title button, and must distinguish a click from a drag via a small pointer-movement threshold (same principle this codebase already uses in `useStackGestureNavigation`'s click-suppression-after-drag idiom) so existing click behavior on the title and header action buttons keeps working.
- **Dim-when-collapsed hook point**: `ComponentConfigSection` (`components/Panel/index.tsx:410-484`) already renders `data-open={open ? 'true' : 'false'}` on its root `<section>` — dimming is a pure CSS addition keyed off `[data-open='false']`, no new markup.
- **Hover-intent hook point**: `ConfigScopeRenderer` (`components/Panel/config/ConfigScopeRenderer.tsx`) already owns `[open, toggle]` from `useConfigScopeOpenState` and is the single call site instantiating every `ComponentConfigSection` — the natural place to read the new hover-intent config fields and wire a pointer-enter timer that calls `toggle()` only when `!open`.

## Bug: dead space in an expanded section body

**Not fully root-caused from static reading alone — the screenshot shows a large blank region whose owning section isn't unambiguously identifiable from the crop** (the visible collapsed "WORDMARK ▶" header sits directly below the empty area, which is likely the tail end of a *different*, currently-expanded section scrolled mostly off the top of the screenshot, not WORDMARK's own disclosure). Two candidate mechanisms, in order of likelihood based on code read so far:

1. **The `grid-template-rows: 0fr ↔ 1fr` disclosure trick** (`Panel.module.css:693-720`) has a known fragility class: `1fr` sizes to the container's content *at layout time*, and if a **nested `Sect`** (`components/Panel/index.tsx:796-851`, the sub-accordion inside a scope like "Surface"/"Shadow response") expands or collapses independently *after* its parent `ComponentConfigSection`'s own disclosure has already settled, nothing forces the parent to re-measure. `.sectionDisclosureInner`'s `clip-path: inset(0 -9999px 0 -9999px)` (added specifically to avoid the cross-axis `overflow` bug documented in the surrounding comment, `Panel.module.css:724-740`) clips *exactly at the row's current computed box*, not at content bounds — so a mismatch between the parent's frozen row height and its child's real content height reads as either clipped content or dead space depending on which direction the mismatch runs.
2. A conditionally-rendered control block (e.g. a field gated by `visibleWhen`, or a lazily-mounted preview widget — the small boxed element visible in the bottom-right of the screenshot's red outline looks like exactly such a widget) whose visible content is legitimately shorter than a space reserved for it elsewhere.

**Do not blind-fix this.** First implementation step: reproduce live with the dev server + browser devtools, identify the actual `data-open='true'` section whose `.sectionDisclosure`/`.sectionContent` box height doesn't match its rendered content's `scrollHeight`, and confirm which of the two mechanisms above (or a third one) is actually responsible. Once confirmed:
- If it's mechanism 1 (stale grid-track sizing from nested/dynamic content): replace the implicit `1fr` sizing with an explicit, `ResizeObserver`-measured `max-height: {measuredPx}px` transition on `.sectionDisclosure`/`.sectionContent` — the standard robust fix for "CSS auto-height animation gets a wrong size when content changes after the animation locks in," strictly more correct than the current implicit-`fr` approach for content that can change shape post-mount (a nested `Sect` toggling, a `visibleWhen` field appearing/disappearing). Preserve the existing `clip-path` overflow handling and its documented cross-axis rationale — that fix stays correct regardless of how the row height is computed.
- If it's mechanism 2: the fix is narrower — either the reserved space should track the widget's real size, or the widget itself has a broken intrinsic-size (e.g. an aspect-ratio box using a stale/huge fallback height, similar to other "huge reserved height for a WebGL preview" bugs elsewhere in this codebase's own history).

## Post-implementation note: some field names evolved during build

Sections above describe the *original* design; a few fields changed shape once real implementation surfaced better options (documented in each file's own comments, not restated here in full):
- `dragSettleDurationMs`/`dragSettleEasing` → replaced by `dragSettleStiffness`/`dragSettleDamping`/`dragSettleMaxDurationMs` — a real damped-spring integration (same vocabulary/pattern as `SplitColumnCardStackConfig.verticalEdgeSpringStiffness`/`-Damping`), not a CSS-eased duration, since "damping on release" was requested literally.
- `dragOpacityTransitionMs`/`dragOpacityTransitionEasing` were added — the original plan's opacity fade had no transition timing at all wired in (a real bug caught during implementation: the value changed but nothing animated it).
- `inactiveSectionDimDurationMs`/`inactiveSectionDimEasing` were added, replacing a hardcoded `var(--panel-motion-fast) ease`.
- `shellOpenDurationMs`/`shellCloseDurationMs`/`shellEasing` were added — a *third* motion surface (the launcher↔panel swap itself, `panelEnter`/`launcherEnter` keyframes) turned out to be separately hardcoded, distinct from the per-row disclosure timing this plan already covered.

## Follow-up: top-edge clipping when a collapsed launcher expands, or the open panel is dragged, near the viewport's top edge

**Operator-reported, with a screenshot**: `.panelFrame` is anchored via CSS `bottom` and grows upward as content requires — the only direction it ever grew before this fix. Two distinct interaction paths produce the same visible symptom (the panel's header/search/tabs render above `y=0`, clipped by the browser viewport, with no way to scroll to them):

1. **A collapsed launcher dragged near the top edge is then clicked open.** The expanded panel doesn't know in advance how tall it will render (its content determines that), so it can't simply be positioned by shrinking a known box — it needs to decide, once, which edge to grow *from*.
2. **An already-open panel is dragged near the top edge by its header.** Here the box's height is already fully known/rendered; dragging it just translates an existing box, and nothing was re-clamping that translation against the viewport bounds the way the *drag itself* is clamped everywhere else.

These needed two different, complementary fixes — fixing only #1 (which is what an earlier pass in this session addressed) left #2 open, which is almost certainly what was still visibly broken.

### Fix for #1 — `components/Panel/usePanelVerticalAnchor.ts` (new file)

A standard "flip if not enough room" popover-positioning check, decided once per open transition (not continuously, so it can't visibly flip mid-animation):
- Tracks the collapsed launcher's real `getBoundingClientRect()` continuously while collapsed (including through drags) — by the time `isOpen` flips true, React has already swapped the launcher DOM node for the full panel section in the same commit, so there's nothing left to measure at that exact moment; the last known collapsed position has to already be on hand.
- On open, compares space above vs. below that last known position (`window.innerHeight - rect.bottom` vs `rect.top`). If there's more room below, `.panelFrame` switches from its default `bottom`-anchored/grow-upward behavior to a `top`-pinned/grow-downward one.
- The pinned `top` is clamped to at least a `VISIBLE_MARGIN_PX` (24px) safety margin even if the raw collapsed position was itself slightly negative (possible since the drag clamp for a *collapsed* launcher deliberately only guarantees a small grabbable sliver stays reachable near an edge, not that the whole launcher sits fully on-screen).
- `PanelShell`'s `shellStyle` computes `--panel-max-height` from whichever edge is actually pinned (`components/Panel/index.tsx`, the `verticalAnchor.mode === 'down'` branch), so `.panel`'s own `max-height` (`components/Panel/Panel.module.css`) can never let it overflow the viewport regardless of anchor mode. `data-anchor={verticalAnchor.mode}` on `.panel` flips `transform-origin` to `right top` in this mode so the existing fade/scale-in entrance still originates from the correct edge.

### Fix for #2 — `components/Panel/usePanelDrag.ts`'s `clampOffset`, now strictness-aware

`clampOffset` gained a `strict: boolean` parameter (`isOpen` is threaded into `usePanelDrag` and read via a ref at drag-release time specifically so it doesn't need to be a dependency of the drag lifecycle callbacks, which would otherwise tear down/re-attach the window pointer listeners mid-gesture):
- `strict: false` (collapsed launcher, unchanged): only a `VISIBLE_MARGIN_PX` sliver of the box must stay reachable — the existing, intentional "off-screen floating action button" affordance.
- `strict: true` (open panel): the box's *entire* top and bottom edge must stay within the viewport — computed from the box's own live-measured `rect.height` at the moment of release, not a theoretical formula, so it self-corrects even in the (narrower) case where the panel opened in "grow downward" mode and was then dragged further before release.

This clamp is only applied at drag *release* (via the existing damped-spring settle snapping to the newly-clamped target), matching the existing UX where the gesture itself follows the pointer 1:1 and only the release corrects/settles — not a live drag-time hard stop.

### Round 2 — a real bug in fix #1's own math, caught after a live operator test

Fix #1 above shipped with a genuine defect, only caught once the operator actually tested it (screenshots showed the panel clipped *worse* than before — pushed further off-screen, not fixed): `topPx` was derived directly from the launcher's raw, live `getBoundingClientRect().top` — a value that **already includes** whatever drag offset was currently applied via `.panelFrame`'s own `transform`. Once open, that *same* `transform` (driven by `usePanelDrag`'s still-unchanged `offset` state) kept being applied **on top of** the new `top: {topPx}px`, double-counting the offset. Concretely: launcher dragged up 700px, live `rect.top` measured as 48px (already reflecting that drag) → `topPx` set to 48 → final rendered position `48px (CSS top) + (-700px) (transform, still applying) = -652px` — translated *twice* as far off-screen as before the "fix."

**Corrected in `components/Panel/usePanelVerticalAnchor.ts`**: the collapsed-rect tracker now also stores the drag offset at the moment of capture (`offsetYAtCapture`). The decision effect still clamps against the *live* (offset-inclusive) position to decide direction and the safe final on-screen top (`clampedLiveTop = Math.max(VISIBLE_MARGIN_PX, rect.top)`), but derives the **CSS** `topPx` by subtracting that captured offset back out (`topPx = clampedLiveTop - offsetYAtCapture`) — so that once the still-applying `transform` adds the offset back in at render time, the sum reproduces exactly the intended clamped position instead of applying it twice. This also required correcting `PanelShell`'s own `--panel-max-height` calc (`components/Panel/index.tsx`), which was using the CSS-only `topPx` (offset subtracted out) to budget remaining vertical space — it now adds the live `dragOffsetY` back in first, since the max-height budget needs the *actual* rendered top position, not the offset-corrected CSS value.

### Round 3 — the real underlying bug: 'up' mode's height budget never accounted for drag position at all

**Operator-reported, with a screenshot**: dragging the collapsed launcher to the vertical *middle* of the viewport, then opening it, still let the expanded panel poke off the top of the screen. This is a different failure from rounds 1–2 — the anchor-flip logic itself was working correctly (more room above than below at that position, so 'up' mode — grow upward — was the right call), but 'up' mode's `--panel-max-height` (`components/Panel/index.tsx`) was still using the **original static formula**: `100dvh - safe-area-bottom - 12px - elevation - shadow`. That formula silently assumes the frame sits at its default, undragged bottom-right corner, where it really does have almost a full viewport of room above. Once the frame is dragged anywhere else — the vertical middle, in the reported case — the actual room above its current position is far less than that formula assumes, but nothing was capping content height to the *real*, current amount of room. This was the actual root cause rounds 1–2 never touched, since both only modified the 'down'-mode path.

**Fix**: `usePanelVerticalAnchor` no longer only decides a direction — it now also computes a live `maxHeightPx`, for *both* directions, directly from the collapsed launcher's own measured position (`window.innerHeight - rect.bottom` worth of room for 'up' mode growing upward from its current bottom edge, `window.innerHeight - rect.top` worth of room for 'down' mode growing downward from its current top edge), each capped with the same `VISIBLE_MARGIN_PX` safety margin at the far edge. `PanelShell`'s `--panel-max-height` now uses this live number directly (`${maxHeightPx}px`) whenever it's available, falling back to the original static formula only for the one edge case where nothing has been measured yet (a controlled `isOpen` prop set true before the shell was ever rendered collapsed). This is a strictly more correct replacement for the static formula in every case, not just the reported one — it also means the frame's real elevation-shadow clearance is automatically reflected (since it's baked into the live measurement) rather than needing a separate manually-subtracted term.

Re-verified: `tsc --noEmit` clean, `vitest run components/Panel` unchanged (same 3 pre-existing failures). Still no browser-automation tool in this session — needs a live check dragging the launcher to several positions (top edge, vertical middle, bottom-right default) and confirming the expanded panel never extends past either the top or bottom of the viewport in any of them.

### Round 4 — the anchor budget never recomputed when the browser window itself was resized while the panel stayed open

**Operator-reported, with a screenshot**: a non-maximized, deliberately short Chrome window showed the open panel's content ("Gaussian amplitude 0.33", a mid-list row) rendering essentially flush with the very top of the page — well past a `VISIBLE_MARGIN_PX` sliver, a full clamp failure, not a narrow-margin issue. Traced by hand against the Round 3 fix's own math (still no browser-automation tool available to reproduce live): Round 3's `maxHeightPx` decision only re-runs on an `isOpen` *transition* (deliberately, per its own doc comment — recomputing mid-open would visibly flip the anchor under the user). That's correct for the case Round 3 was built for (drag position), but leaves a distinct gap: if the operator opens the panel on a taller window and then **shrinks the browser window's own height while the panel stays open**, `maxHeightPx` stays frozen at whatever budget the original, taller viewport allowed — the box's own CSS `top`/`bottom` anchor position doesn't move on a height-only resize (a `bottom: Npx` fixed element always stays exactly N px from the viewport's bottom edge, whatever height that viewport now is), but the *budget* needs to shrink to match, and nothing was doing that.

**Fix**: `usePanelVerticalAnchor` gained a second effect — a `window.resize` listener, active only while the panel is open — that recomputes `maxHeightPx` using the exact same math as the initial decision, but sourced from the now-already-open frame's own live `getBoundingClientRect()` instead of a collapsed-launcher snapshot (both are equally valid live-position sources; which one is available differs only by which state the shell happens to be in at measurement time). Deliberately keeps whichever `mode` ('up'/'down') is already active rather than re-deciding direction on resize — flipping which way an already-visible, open panel grows out from under the operator mid-resize would be its own jarring regression; shrinking its height budget in place is not.

Verified: `tsc --noEmit` clean, `vitest run components/Panel` unchanged (same 3 pre-existing failures), dev server smoke-tested and **killed immediately after the check** (see `feedback_reserved_port_3000.md`'s 2026-08-29 addendum — an earlier round of this same investigation left a dev server orphaned for about an hour before being caught, a real process-hygiene incident independent of this bug fix itself). Still not visually confirmed in a live browser — the specific repro (open on a tall window, shrink it, confirm the panel's own budget shrinks to match rather than staying frozen) needs a human check.

## Follow-up: extend the draggable area to the panel's own padded border, and fix a dead zone in the header

**Operator-reported, with two screenshots**: dragging didn't trigger over a specific area near the header's right edge, and separately, the panel's own visible padding gutter (the empty border-like space around its content — a tall strip running the full height along the right edge) wasn't part of the draggable area at all, despite visually reading as "the panel's own chrome," not content.

**Root cause of the dead zone**: `.scrollArea` (`components/Panel/Panel.module.css`) deliberately extends its own box edge-to-edge across the panel's true width via a negative `margin-inline`/matching `padding-inline` pair (so its `overflow-x: hidden` clips shaded-subgroup box-shadow bleed at the true panel edge, not the padded content edge — see that rule's own pre-existing doc comment). A side effect: the visible padding gutter running down the left/right edges below the header is literally `.scrollArea`'s own empty `padding-inline` space, not `.panel`'s padding — and neither `.panel`'s root nor `.scrollArea` had any drag listener at all, since only `.panelHeader` (which stops at the *padded* content edge, not the panel's true visual edge) did.

**Fix**: `usePanelDrag.ts` gained a second handler set, `backgroundHandleProps`, gated on `event.target === event.currentTarget` before starting a drag — meaning it only fires when a pointerdown lands directly on the background element's own empty box, never on any descendant (button, row, slider, or otherwise). This is the standard safe pattern for making a "background" area draggable without stealing pointer events from real interactive content. Spread onto two elements in `components/Panel/index.tsx`:
